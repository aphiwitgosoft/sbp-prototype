## 3. ภาพรวมการทำงาน

```
① ดึงรายการงานค้าง
      │  ไม่มีข้อมูล ──▶ log แล้วจบ (ไม่ส่งอีเมลเลย)
      ▼
② แบ่งเป็น 3 ช่วงอายุ (30-36 / 45-51 / 60-66)
      ▼
③ แต่ละช่วง: จัดกลุ่มตามโซน → ประกอบตาราง HTML → ส่งอีเมล
```

### 🔴 เรื่องที่ต้องรู้ก่อนอย่างอื่น — เป็น "ช่วง" ไม่ใช่ "เกิน"

```java
if (waitDay >= 30 && waitDay <= 36)        dayProcess30.add(...);
else if (waitDay >= 60 && waitDay <= 66)   dayProcess60.add(...);
else if (waitDay >= 45 && waitDay <= 51)   dayProcess45.add(...);
```

**ทั้งสามเป็นช่วงปิด 7 วัน** — ไม่ใช่ `>= 30 วัน`

| อายุงาน | เตือนไหม |
|---|---|
| 1–29 วัน | ❌ |
| **30–36 วัน** | ✅ เตือนครั้งที่ 1 |
| **37–44 วัน** | 🔴 **ไม่เตือนเลย** |
| **45–51 วัน** | ✅ เตือนครั้งที่ 2 |
| **52–59 วัน** | 🔴 **ไม่เตือนเลย** |
| **60–66 วัน** | ✅ เตือนครั้งที่ 3 |
| **67 วันขึ้นไป** | 🔴 **ไม่เตือนอีกเลยตลอดกาล** |

> 📌 **เจตนาที่เดาได้** — job รันสัปดาห์ละครั้ง (ทุกวันจันทร์) ช่วงกว้าง 7 วันจึงดู "พอดี" กับรอบรัน
>
> 🔴 **แต่รับประกันไม่ได้ว่าจะเตือนพอดี 1 ครั้ง** — เพราะ **"วัน" ที่นับคือ *วันทำการ* ไม่ใช่วันปฏิทิน**
> (K2 คำนวณจากปฏิทิน `Franchise Working Day` · `PiWorkingHourPerDay = 9`)
>
> | สถานการณ์ | อายุงานเพิ่มใน 1 สัปดาห์ปฏิทิน | ผล |
> |---|---|---|
> | สัปดาห์ปกติ (จ.–ศ.) | ~5 วันทำการ | อยู่ในช่วงเดิม → **เตือนซ้ำ** |
> | มีวันหยุดยาว | 2–3 วันทำการ | ยิ่งเตือนซ้ำ |
> | ถ้านับ 7 วันทำการพอดี | 7 | เตือนครั้งเดียว (กรณีในอุดมคติเท่านั้น) |
>
> 🔴 **ปกติจะเตือนซ้ำ ไม่ใช่ครั้งเดียว** — เอกสารที่อายุ 30 วันทำการวันจันทร์นี้
> สัปดาห์หน้าจะเป็น ~35 วันทำการ ซึ่ง **ยังอยู่ในช่วง 30–36** → ได้เมลอีกฉบับ
>
> ✅ **ต้องออกแบบการกันเตือนซ้ำจาก notification state จริง** ไม่ใช่พึ่งความกว้างของช่วง (ดูหัวข้อ 9)

> 🔴 **แต่ผลข้างเคียงคือ "เงียบหลัง 66 วัน"** — เอกสารที่ค้าง 3 เดือนจะไม่มีใครเตือนอีกเลย
> ทั้งที่นั่นคือกรณีที่ควรดังที่สุด · **ต้องเคาะว่าจะเพิ่มช่วงที่ 4 แบบ "เกิน 66 วัน" ไหม** (ดูหัวข้อ 9)

> ⚠️ **ถ้า job ไม่ได้รันสัปดาห์ใดสัปดาห์หนึ่ง (เครื่องล่ม/deploy) เอกสารในช่วงนั้นจะพลาดการเตือนถาวร**
> เพราะสัปดาห์ถัดไปอายุงานจะเลยช่วงไปแล้ว

## 4. ขั้นที่ ① — ดึงรายการงานค้าง

### ระบบเดิม — ดึงจาก **K2 SmartObject REST**

```java
url.append(FgiConstant.MANDAYSMARTOBJECT);
// http://k2app-uat.cpall.co.th:8888/SmartObjectServices/rest/CPA/Franchise/FIA/SMOs/
//   CPA.Franchise.FIA.SMO.VFgiImpactStoreWorkingHour/List
//   ?$format=json&PiZoneName=Franchise%20Working%20Day&PiWorkingHourPerDay=9&PiWfStepId=501001
String basicAuth = "Basic " + new String(new Base64().encode(FgiConstant.K2USER.getBytes()));
```

**ไม่ได้อ่านจากฐานข้อมูลเลย** — เรียก REST ของ K2 เพื่อขอ view ที่ K2 คำนวณ "จำนวนวันทำการที่รอ" มาให้แล้ว

| พารามิเตอร์ | ค่า | ความหมาย |
|---|---|---|
| `PiZoneName` | `Franchise Working Day` | ปฏิทินวันทำการที่ใช้นับ |
| `PiWorkingHourPerDay` | `9` | **1 วันทำการ = 9 ชั่วโมง** |
| `PiWfStepId` | **`501001`** (`STEPIDWAIT`) | ขั้นตอนที่เฝ้า |

> 🔴 **"จำนวนวันที่รอ" เป็น *วันทำการ* ไม่ใช่วันปฏิทิน** — K2 คำนวณให้จากปฏิทิน `Franchise Working Day`
> ที่หักวันหยุดออกแล้ว · **ระบบใหม่ต้องคำนวณเองและต้องรู้ว่าใช้ปฏิทินไหน** (ดูหัวข้อ 9)

### 🔴 A — `setConnectTimeout(0)` / `setReadTimeout(0)` = รอไม่มีที่สิ้นสุด

```java
myURLConnection.setConnectTimeout(0);
myURLConnection.setReadTimeout(0);
```

ใน Java `0` แปลว่า **infinite** — ถ้า K2 ค้าง **job จะค้างตามไม่มีกำหนด**
และเนื่องจากรันสัปดาห์ละครั้ง **อาจค้างข้ามสัปดาห์โดยไม่มีใครสังเกต**

> ⚠️ ต่างจาก Job 8b ที่ **ไม่ได้ตั้ง** timeout (ใช้ค่า default) · **ที่นี่ตั้งเป็น 0 อย่างจงใจ**

### 🔴 B — กรองแค่ขั้นตอนเดียว (`STEPIDWAIT = 501001`)

```java
if (FgiConstant.STEPIDWAIT.equalsIgnoreCase(impactProcess.get(index).getStepID())) { ... }
```

**เฝ้าเฉพาะขั้นตอนเดียวของ workflow** — งานที่ค้างอยู่ขั้นอื่น (GM · AVP · หน่วยงานส่งเสริมธุรกิจ)
**ไม่ถูกเฝ้าเลย** ทั้งที่ flow มี 5 ขั้น

> 🔴 **ระบบใหม่มี 5 ขั้น (06 · 08 · 01 · 02 · 03)** — ต้องเคาะว่าเฝ้าขั้นไหนบ้าง (ดูหัวข้อ 9)

### ระบบใหม่ — อ่านจาก DB โดยตรง

**มติ 2026-09-09:** batch job **ห้ามเรียก `@srm/glb-workflow`** — workflow lib ใช้กับ flow K2 เท่านั้น

| | ทำอะไร |
|---|---|
| ❌ **ห้าม** เรียก `getPendingFlowByUser()` | เป็น inbox **รายคน** · job ต้องการงานค้าง**ทั้งระบบ**เพื่อคิดอายุ |
| ✅ **ให้** อ่าน `sps_store.workflow_transaction` ด้วย SQL **อ่านอย่างเดียว** | **ห้ามเขียนตารางของ engine เด็ดขาด** |

> 🔴 **`sps_store.workflow_transaction` ไม่มี PK และไม่มี index เลย** บน 19,327 แถว
> (`DECISIONS` ข้อ **4.1** · DP-2) — คิวรีของ job นี้จะเป็น **seq-scan ทุกครั้ง**
> รันสัปดาห์ละครั้งจึงพอรับได้ แต่ **ต้องรู้ตัวและวัดเวลา**

#### ✅ แก้ 2026-09-14 — `SET LOCAL` ต้องอยู่ใน transaction เดียวกับคิวรี

โค้ดรุ่นแรกยิง `SET LOCAL statement_timeout` เป็นคำสั่งเดี่ยวผ่าน connection pool
ซึ่ง **ไม่มีผลเลย** — ทดสอบกับ PostgreSQL 16 จริงแล้วได้

```
WARNING:  SET LOCAL can only be used in transaction blocks
SHOW statement_timeout;  →  0      -- ค่าถูกทิ้ง
```

ซ้ำร้าย คิวรีถัดไปอาจได้ connection คนละตัวจาก pool ด้วย
timeout ที่ตั้งไว้กัน seq-scan ค้างจึง**ไม่เคยทำงานสักครั้ง**

ของใหม่ครอบ `dataSource.transaction()` แล้วยิงทั้ง `SET TRANSACTION READ ONLY`
และ `SET LOCAL statement_timeout` บน connection เดียวกับ `SELECT`

| | ผลที่ทดสอบจริง |
|---|---|
| `SET LOCAL` ใน transaction | `statement_timeout = 12345ms` ✅ |
| `SET TRANSACTION READ ONLY` | `DELETE` → `ERROR: cannot execute DELETE in a read-only transaction` ✅ |

> ✅ `READ ONLY` เป็น**ตัวกันทางฐานข้อมูล**ว่า job นี้แตะตารางของ engine แบบอ่านอย่างเดียวจริง
> ไม่ใช่แค่คำสัญญาในเอกสาร

## 5. ขั้นที่ ② ③ — จัดกลุ่มและส่งอีเมล

### จัดกลุ่มสองชั้น

```
ช่วงอายุ (30 / 45 / 60)
   └── โซนของร้านที่ถูกกระทบ (zoneI)
          └── 1 อีเมล
```

**1 อีเมล = 1 โซน × 1 ช่วงอายุ** — ถ้ามี 5 โซนและครบทั้ง 3 ช่วง จะส่ง **15 ฉบับ**

### ผู้รับ

```java
sendMailHTTP(email.get(GM_GROUP_ID_INT),      // 38 = GM
             email.get(OPT_GROUP_ID_INT),     // 15 = OPT (ผู้จัดการเขต)
             regionList.get(index), period, DateUtils.getCurrentBuddhistDate(), sendList)
```

| กลุ่ม | id | บทบาท |
|---|---|---|
| `GM_GROUP_ID` | **38** | GM |
| `OPT_GROUP_ID` | **15** | OPT / ผู้จัดการเขต |

**ดึงอีเมลจาก `business_user` ของระบบ SBP เดิม** ผ่าน `selectEmail()` ที่จัดกลุ่มตามโซน

> 📌 **group id 15 และ 38 เป็นชุดเดียวกับที่ Job 8b ใช้หา `opt_dv_user_id`/`opt_gm_user_id`**
> — เป็นค่าคงที่ของ auth-backend ที่ต้องยืนยันว่ายังใช้ได้ในระบบใหม่

### เนื้อหาอีเมล — ตาราง HTML

`getTable()` ประกอบตารางด้วย `HtmlParser` มีหัวตารางซ้อนสองชั้น:

| ลำดับที่ | ร้านเปิดใหม่ (3 คอลัมน์) | ร้านใกล้เคียงที่รอการพิจารณา (3 คอลัมน์) | จำนวนวันที่รอดำเนินการ |
|---|---|---|---|
| | ร้านสาขา · ภาค · วันที่เปิดร้าน | ↑ เหมือนกัน | |

> ⚠️ **วันที่ในอีเมลเป็น พ.ศ.** — `DateUtils.getCurrentBuddhistDate()`
> เป็นอีเมลถึงคน จึงเหมาะสม **แต่ต้องไม่ให้ พ.ศ. ปนเข้า DB** (กติกาทั้งระบบ)

### 🔴 C — ไม่มีข้อมูลเลย = ไม่ส่งอะไรเลย

```java
if (jsonArray.size() == 0) {
    LogUtils.info(SendMailReport.class, "No data from K2");
} else { ... }
```

**ถ้า K2 คืนอาร์เรย์ว่าง job จะเงียบสนิท** — ไม่ส่งเมลบอกว่า "สัปดาห์นี้ไม่มีงานค้าง"

| สาเหตุที่ได้อาร์เรย์ว่าง | ความหมายจริง |
|---|---|
| ไม่มีงานค้างจริง ๆ | ✅ ข่าวดี |
| **K2 ตอบ 200 แต่ข้อมูลผิดพลาด** | 🔴 ระบบพัง |
| **`PiWfStepId` เปลี่ยนไป** | 🔴 กรองไม่เจออะไรเลย |

> 🔴 **แยกไม่ออกจากภายนอก** — ถ้า SmartObject เปลี่ยนโครงหรือ step id เปลี่ยน
> job จะเงียบทุกสัปดาห์โดยไม่มีใครรู้ · **ระบบใหม่ต้องรายงานทุกครั้งว่าตรวจไปกี่รายการ**

### 🔴 D — `status && check` ตัดสินผลแบบเปราะ

```java
if (sendMailHTTP(...)) { status = true; }
else { check = false; }
...
return status && check;
```

| สถานการณ์ | `status` | `check` | ผลลัพธ์ |
|---|---|---|---|
| ส่งสำเร็จทุกโซน | `true` | `true` | ✅ `true` |
| ส่งล้มบางโซน | `true` | `false` | ❌ `false` |
| **ไม่มีโซนให้ส่งเลย** | `false` | `true` | ❌ **`false`** ทั้งที่ไม่มีอะไรผิด |

> 🔴 **ช่วงอายุที่ไม่มีงานค้างจะถูกรายงานว่า "Failed"** — log จะขึ้น
> `-----Send Email 45 day to GM Failed-----` ทั้งที่แค่ไม่มีงานในช่วงนั้น
> **ทำให้ log แยกไม่ออกระหว่าง "ไม่มีงาน" กับ "ส่งไม่สำเร็จ"**

### ⚠️ ไม่มี exit code

```java
} catch (Exception e) {
    LogUtils.error(SendMailReport.class, e);
    LogUtils.info(SendMailReport.class, "===***Job Send Email Failed***===");
}
```

`main` จับ exception แล้ว log อย่างเดียว — **process ออกด้วย 0 เสมอ** (เหมือน Job 2 · L3)

| **L2** | 🔴 **ไม่มีข้อมูล = เงียบสนิท** | `if (jsonArray.size() == 0) { log("No data from K2"); }` — ไม่ส่งอะไรเลย · **แยกไม่ออกระหว่าง "ไม่มีงานค้าง" กับ "query/mapping พัง"** | รายงาน `pendingTotalCount` ทุกครั้ง แม้เป็น 0 |
| **L3** | 🔴 **`status && check` ทำให้ "ไม่มีงาน" กลายเป็น "Failed"** | ช่วงอายุที่ไม่มีงานจะ log `-----Send Email 45 day to GM Failed-----` | แยก **"ไม่มีอะไรให้ส่ง"** ออกจาก **"ส่งไม่สำเร็จ"** |
| **L4** | **เฝ้าขั้นตอนเดียว** | `STEPIDWAIT = 501001` เท่านั้น · flow มี 5 ขั้น | ระบุขอบเขตให้ครบพร้อมเหตุผล |
| **L5** | **ดึงข้อมูลผ่าน K2 REST ด้วย Basic Auth + credential ฝังโค้ด** | `K2USER = "7ELEVEN\bpmk2_fcs:SupportGSSF2"` (`FgiConstant.java:23`) | อ่าน DB โดยตรง · `DECISIONS` ข้อ **4.6** — credential เดิมต้อง rotate |
| **L6** | **ไม่มี exit code** | `main` catch แล้ว log อย่างเดียว | exit non-zero เมื่อล้มเหลว (เหมือน Job 2 · L3) |
| **L7** | **`else if` เรียง 30 → 60 → 45** | ช่วงไม่ทับกันจึงไม่พัง แต่**อ่านแล้วชวนสับสน** | เรียงตามลำดับ หรือใช้โครงสร้างข้อมูลแทน if-chain |
| **L8** | **ประกอบ HTML ด้วยการต่อสตริง** | `HtmlParser.getTHRowspan2(...)` ต่อกันทีละ tag | ใช้ **template EM-04/EM-05** จาก `email_template` |
| **L9** | **ส่งเมลเอง ไม่ผ่าน lib** | `sendMailHTTP` | ใช้ **`@gosoft-sbp/email-lib`** — lib เขียน `email_sent` ให้เอง |

> ⚠️ **L2 + L3 รวมกันทำให้ job นี้ "โกหกสองทาง"**
> ไม่มีงานค้างจริง → log ว่า **Failed** · ระบบพังจนไม่เห็นงานเลย → log ว่า **No data** แล้วเงียบ
> **คนดูแลจึงอ่าน log ของ job นี้แล้วสรุปอะไรไม่ได้เลย**
>
> และเนื่องจากงานที่ค้างคือ **เอกสารที่ทำให้ร้านได้เงิน** ความเงียบตรงนี้แปลว่า
> **ร้านรอเงินนานขึ้นโดยไม่มีใครรู้ว่ามีเรื่องค้างอยู่**
