## 3. ภาพรวมการทำงาน 4 ขั้น

```
① ตรวจก่อนว่า "งวดนี้เคยนำเข้าไปแล้วหรือยัง"
      │  เคยแล้ว ──▶ จบทันที (ถือว่าสำเร็จ) ไม่ทำอะไรเลย
      ▼
② ดึงข้อมูลทั้งงวดจากวิว ALLMAP (SELECT DISTINCT)
      │  ไม่มีข้อมูล ──▶ จบทันที (ถือว่าสำเร็จ)
      ▼
③ insert ทีละก้อน ก้อนละ 10,000 แถว
      ▼
④ นับเทียบ: insert ครบเท่าที่ดึงมาไหม → ส่งเมลแจ้งผล
```

> 📌 **ไม่มีขั้น "เติมข้อมูลจาก master" และไม่มีขั้น "ตัดสิน" แบบ Job 2**
> ข้อมูลจากวิวถูกเขียนลงตารางตรง ๆ เกือบทั้งหมด

### 🔴 เรื่องที่เข้าใจผิดกันบ่อยที่สุด — ขั้น ① ไม่ใช่ "ล้างแล้วนำเข้าใหม่"

**ระบบเดิม *ไม่มีคำสั่ง DELETE เลยแม้แต่จุดเดียว*** (ยืนยันด้วยการค้นทั้ง `fcsJar/` — ไม่มี `DELETE FROM FGI_IMPACT_COMPETITOR` ที่ไหน)

สิ่งที่ขั้น ① ทำจริงคือ:

```java
int countRec = importService.countRowImpactCompetitor(year, month, zoneArr);
if (countRec != 0) {           // มีข้อมูลของงวดนี้อยู่แล้ว
    informBean.setNote("[Not] !! Import Impact Competitor Because hava data period ...");
    informBean.setStatus(JOB_STATUS_SUCCESS);   // ⚠️ ถือว่า "สำเร็จ"
    sendMailToAdmin(...);
    return;                    // ออกทันที ไม่ insert อะไรเลย
}
```

→ **มีข้อมูลอยู่แล้ว = ข้ามทั้งงวด ไม่ใช่ล้างแล้วนำใหม่**
ถ้าอยากนำเข้าใหม่ ต้องมีคน **ลบข้อมูลงวดนั้นด้วยมือ** ก่อน

> ⚠️ **ผลที่ตามมาที่ต้องรู้** — ถ้ารอบแรกนำเข้าไม่ครบ (เช่น ALLMAP ยังใส่ข้อมูลไม่เสร็จ)
> การรันซ้ำ **จะไม่ช่วยอะไรเลย** เพราะเห็นว่ามีข้อมูลแล้วก็ข้ามทันที **และยังรายงานว่าสำเร็จด้วย**
> ข้อมูลจะขาดไปเงียบ ๆ จนกว่าจะมีคนสังเกตเห็นที่หน้าจอเอกสาร

## 4. ขั้นที่ ① — ตรวจว่างวดนี้เคยนำเข้าหรือยัง

### SQL ของระบบเดิม

```sql
select count(1) count_rec from fgi_impact_competitor where year = ? and month = ?
```

**นับทั้งงวด ไม่แยกร้าน ไม่แยกโซน** — เจอแถวเดียวก็ถือว่า "งวดนี้ทำแล้ว"

> 💡 โค้ดกรองโซนมีอยู่จริงแต่ **ถูก comment ทิ้งไว้** (`ImportJdbc.java` บรรทัด 206-209)
> และตัวแปร `zoneArr` ก็ถูกประกาศเป็น `{}` แล้วไม่เคยถูกเติมค่าเลย (`ImportController.java:486`)
> → **Job 3 ไม่มีความสามารถกรองโซน** ต่างจาก Job 2

### Argument ที่รับได้ — **`YYYY|MM` เท่านั้น**

| กรณี | ผล |
|---|---|
| ไม่ส่ง argument | ใช้ **เดือนที่แล้ว** (`addMonth(getDateNow(Locale.US), -1)`) |
| `2569\|06` | ใช้งวดนั้น |
| ส่งมา 1 ส่วน หรือ ส่วนใดว่าง | **`NullPointerException`** — `"Missing right Parameter!!, The correct format parameter is YYYY\|MM"` |
| ส่งมา **3 ส่วนขึ้นไป** | **`NullPointerException`** เหมือนกัน |
| รูปแบบวันที่ไม่ถูก | **`ParseException`** — `"Can't parse Date format yyyy/MM"` |

> ⚠️ **ห้ามลอกรูปแบบ `ZONES|YYYY|MM` ของ Job 2 มาใช้** — Job 3 จะโยน exception ทันทีถ้าเจอ 3 ส่วน

### 🔴 พ.ศ. หรือ ค.ศ. — ปัญหาเดียวกับ Job 2 และตัว validate ก็จับไม่ได้

**ค่าตั้งต้นในโค้ดให้ ค.ศ.** — `getDateNow(Locale.US)` ใช้ปฏิทิน Gregorian จึงได้ `2026`
**แต่ตัวอย่าง argument ในเอกสาร/ผังของทีมคือ `2569|06`** (พ.ศ.) และไม่มีโค้ดไหนแปลงเลย

**และตัว validate ก็ปล่อยผ่าน** — `isDateValid(year+"/"+month, "yyyy/MM")` ใช้ `SimpleDateFormat`
ซึ่ง `yyyy` รับตัวเลข 4 หลักอะไรก็ได้ → `2569/06` **ผ่านการตรวจสบาย ๆ**
ตัวตรวจนี้จับได้แค่ **เดือนนอกช่วง 1–12** เท่านั้น

> 🔴 **ยังไม่มีหลักฐานจากฐาน ALLMAP จริง** — แยกสองอย่างนี้ให้ขาดจากกัน:
>
> | | สถานะ |
> |---|---|
> | **ตัวอย่างในเอกสาร/ผังเดิม** (`2569\|06`) | ✅ ยืนยันได้ — อยู่ใน `job-batch.html` params ของ Job 3 |
> | **ค่าที่ `PERIOD_YEAR` ของวิวต้องการจริง** | ❌ **ยังไม่ได้ตรวจ** — ไม่มี run log หรือผล query มายืนยัน |
>
> **หลักฐานสวนทาง:** ไฟล์ที่ระบบเดิมส่งให้ K2 จริง (`docs/ตัวอย่างไฟล์ที่วางให้ K2 เอาเข้าระบบ/20170609_200402_BPM06003O_.txt`)
> ใช้งวด `05` / **`2017`** ซึ่งเป็น **ค.ศ.**
>
> ✅ **ต้องรัน `SELECT DISTINCT PERIOD_YEAR FROM allmapssa.COMPETITOR_IMPACT_VIEW` ใน environment ที่ถูกต้อง**
> แล้วเก็บ **ผล query · วันที่ · environment · ผู้ยืนยัน** ไว้เป็นหลักฐาน (ดู `DECISIONS` ข้อ 4.4)
>
> ✅ **ไม่ว่าผลเป็นอะไร ระบบใหม่รับ ค.ศ. ที่ input เสมอ** แล้วแปลง **ณ จุดเดียวก่อน bind query**
> และ **ปฏิเสธค่าในช่วง 2500–2599** พร้อมบอกว่าน่าจะส่ง พ.ศ. มา
> **Job 2 และ Job 3 ต้องใช้ calendar contract ชุดเดียวกัน**

### สัญญา input ของระบบใหม่ (JSON ผ่าน `INPUT`)

```json
{ "year": 2026, "month": 6 }
```

| ฟิลด์ | ชนิด | บังคับ | กติกาตรวจ |
|---|---|---|---|
| `year` | integer | ไม่ | **ค.ศ. · 2000–2999** · ไม่ใส่ = ปีของเดือนที่แล้ว · **ปฏิเสธ 2500–2599** |
| `month` | integer | ไม่ | **1–12** · ไม่ใส่ = เดือนที่แล้ว |
| ฟิลด์อื่น | — | — | **unknown field = ปฏิเสธทั้ง job** — โดยเฉพาะ `zones` ที่คนมักใส่มาเพราะเคยชินจาก Job 2 **ทั้งที่ Job 3 ไม่รองรับ** |

> ⚠️ ถ้าจะ **เพิ่ม** ความสามารถกรองโซนให้ Job 3 = **requirement ใหม่** ไม่ใช่การพอร์ตของเดิม
> ต้องเคาะก่อนว่าจะทำหรือไม่ (ดูหัวข้อ 10)

### เขตเวลา

เหมือน Job 2 — คำนวณ "เดือนที่แล้ว" ตามเวลา **`Asia/Bangkok` (UTC+7)**
AWS Batch scheduled event เป็น UTC · รัน `07:00` ของวันที่ 7 เวลาไทย = `00:00` ของวันที่ 7 ใน UTC (ยังวันเดียวกัน)
แต่ถ้าเลื่อนเวลารันไปก่อน `07:00` เมื่อไร **จะข้ามวัน/ข้ามเดือนใน UTC ทันที** จึงต้องระบุ timezone ให้ชัดตั้งแต่แรก

## 5. ขั้นที่ ② — ดึงข้อมูลจากวิว ALLMAP

### SQL ของระบบเดิม

```sql
SELECT distinct *
  FROM allmapssa.COMPETITOR_IMPACT_VIEW
 WHERE PERIOD_YEAR = ? AND PERIOD_MONTH = ?
```

### คอลัมน์ที่อ่านจริง (11 คอลัมน์)

| คอลัมน์ในวิว | เก็บเป็น | หมายเหตุ |
|---|---|---|
| `STORECODE_I` | รหัสร้าน SP ที่ถูกกระทบ | ⚠️ **คีย์เดียวที่ผูกกลับไปหาร้านได้** |
| `COMPET_ID` | **รหัสสาขา**ของคู่แข่ง | → `competitor_store_code` · **ไม่มี FK** (ดูหัวข้อ 7 · ✅ B) |
| **`NAMT`** | ชื่อไทย → `NAME_TH` | ⚠️ **ชื่อคอลัมน์คือ `NAMT` ไม่ใช่ `NAME_TH`** |
| `NAME` | ชื่อแบรนด์อังกฤษ | → `name_en` · ใช้ map หา `brand_code` ด้วย |
| **`BRANCHT`** | ชื่อสาขา → `BRANCH_TH` | ⚠️ **ชื่อคอลัมน์คือ `BRANCHT` ไม่ใช่ `BRANCH_TH`** |
| `ZONE_CODE` · `SUBZONE_CODE` | โซน/โซนย่อย | → `zone_code` · `subzone_code` (เพิ่มลง DDL แล้ว 2026-09-09) |
| `OPEN_DATE` · `CLOSE_DATE` | วันเปิด/ปิดของคู่แข่ง | |
| `PERIOD_YEAR` · `PERIOD_MONTH` | งวด | 🔴 **ยังไม่ยืนยันว่าเป็น พ.ศ. หรือ ค.ศ.** (ดูหัวข้อ 4) |

> ⚠️ **`NAMT` / `BRANCHT` เป็นชื่อคอลัมน์ของวิว ALLMAP จริง ๆ ไม่ใช่พิมพ์ผิดในเอกสาร**
> (`ImpactCompetitorMapper.java` บรรทัด 18 และ 20) — เขียน `NAME_TH` แทนจะได้ `SQLException` ทันที

### 🔴 กับดักของ `SELECT distinct *`

`DISTINCT *` เทียบ **ทุกคอลัมน์ของวิว** ไม่ใช่แค่ 11 คอลัมน์ที่เอาไปใช้

**ถ้าวิวมีคอลัมน์อื่นปนอยู่** (เช่นรหัสแถว · ระยะทาง · timestamp) แล้วสองแถวต่างกันแค่คอลัมน์นั้น
→ **`DISTINCT` ไม่ตัดออก** แต่ 11 คอลัมน์ที่เราเอาไปใช้เหมือนกันทุกประการ
→ **ได้แถวซ้ำเข้าตารางเรา**

> ✅ **ระบบใหม่ต้อง `SELECT DISTINCT <ระบุคอลัมน์>` ไม่ใช่ `DISTINCT *`**
> และต้อง **นับจำนวนที่ถูกตัดจากการ dedup** ลง log เพื่อดูว่าต้นทางส่งซ้ำมากผิดปกติหรือไม่

### เคสที่ต้องระวัง — ALLMAP ไม่มีข้อมูล

```java
if (impactCompetitorList.size() == 0) {
    informBean.setNote("No Data Found");
    informBean.setStatus(JOB_STATUS_SUCCESS);   // สำเร็จ
    return;
}
```

**นี่คือพฤติกรรมที่ตั้งใจ ไม่ใช่บั๊ก** — เดือนที่ไม่มีคู่แข่งเปิดใหม่ใกล้ร้าน SP เลยเป็นเรื่องปกติ **ห้าม throw error**

> ⚠️ **แต่ต้องแยกให้ออกจาก "ต่อฐาน ALLMAP ไม่ได้"**
> `ImportJdbc.selectVImpactCompetitor` **ไม่มี try/catch** จึงโยน exception ออกมาจริงเมื่อต่อไม่ได้ (ต่างจาก Job 2 ที่ `return null` แล้วเกิด NPE — ดู `JOB-02` หัวข้อ 11 · L2)
> ระบบใหม่ต้องคงพฤติกรรมนี้ไว้: **ต่อไม่ได้ = ล้มเหลว · ต่อได้แต่ไม่มีแถว = สำเร็จ**

## 6. ขั้นที่ ③ — insert ทีละก้อน

### ก้อนละ 10,000 แถว

`FgiConstant.NUMBER_FILE_CUT_OFF = 10000` — ตัดเป็นก้อนแล้ว `batchUpdate` ทีละก้อน
**ทุกก้อนอยู่ใน transaction เดียวกัน** (ไม่ได้ commit ทีละก้อน)

### SQL ของระบบเดิม

```sql
INSERT INTO FGI_IMPACT_COMPETITOR
  (STORECODE_I, COMPET_ID, NAME_TH, NAME, BRANCH_TH, ZONE_CODE, SUBZONE_CODE,
   OPEN_DATE, CLOSE_DATE, MONTH, YEAR, DATASOURCE, IMPACT_COMPETITOR_ID)
VALUES (?,?,?,?,?,?,?,?,?,?,?,?, SEQ_FGI_IMPACT_COMPETITOR.NEXTVAL)
```

`DATASOURCE` ใส่ค่าคงที่ `'ALM'` เสมอ (`FgiConstant.DATASOUCE_ALM`)

### ตารางเดิมไม่มี PK และไม่มี UNIQUE

```sql
CREATE TABLE "FCS_FRN"."FGI_IMPACT_COMPETITOR" (
    IMPACT_COMPETITOR_ID NUMBER(*,0),   -- ไม่ได้ประกาศเป็น PRIMARY KEY
    ... );
CREATE INDEX "IDX_FGI_IMPACT_COMPETITOR" ON ... ("STORECODE_I","MONTH","YEAR");  -- INDEX ธรรมดา
```

> 🔴 **ตารางเดิมยอมให้มีแถวซ้ำได้ทุกรูปแบบ** — ไม่มีอะไรกันเลยนอกจากการเช็ค "งวดนี้ทำแล้วหรือยัง"
> 🔴 **`competitor_store_code` เป็น nullable และต้นทางส่งค่าว่างมา 56 แถว**
> PostgreSQL ให้หลาย `NULL` ผ่าน UNIQUE ได้ **แต่ `ON CONFLICT` ก็จะไม่ match แถว NULL เดิมด้วย**
> → แถวรหัสว่างจะ **insert ใหม่ทุกครั้งที่รัน** ถ้าไม่มี identity สำรอง
>
> ✅ **ตารางใหม่จึงไม่ได้ UNIQUE ที่ `competitor_store_code` ตรง ๆ** แต่ใช้คอลัมน์ generated
> `competitor_key` ที่ **ไม่เป็น NULL เลย**:
> `uq_impact_competitor UNIQUE (impact_process_id, competitor_key, period_key)`
> โดย `competitor_key` = รหัสสาขาถ้ามี ไม่งั้น `name:brand|zone|subzone|ชื่อสาขา`
>
> 🔴 **แก้ 2026-09-14 (รอบตรวจที่ยี่สิบสอง)** — ชื่อสาขาต้องเป็น
> `COALESCE(NULLIF(btrim(branch_th), ''), name_th, '')` ไม่ใช่ `COALESCE(branch_th, name_th, '')`
> เพราะ `COALESCE` ข้ามเฉพาะ `NULL` **ไม่ข้ามสตริงว่าง** — และต้นทางเดียวกันนี้
> **ส่งค่าว่างมาจริงแล้ว 56 แถวในคอลัมน์รหัส** จึงต้องถือว่า `branch_th` ว่างได้เช่นกัน
> ถ้าไม่แก้ คู่แข่งคนละร้านที่ brand/zone/subzone เดียวกันจะได้คีย์ `name:b1|z1|s1|` เหมือนกันเป๊ะ
> แล้ว**หายไปหนึ่งร้านเงียบ ๆ** ตอนชน UNIQUE · พิสูจน์กับ PostgreSQL จริงแล้ว
> ⚠️ ฝั่ง TypeScript (`competitor-key.ts`) ต้องให้ผลตรงกันเป๊ะ เพราะ Job 7 เอาคีย์ฝั่ง TS
> ไป prune แถวในเอกสาร — guard คือ `__svc__/competitor-key-ddl.svc.spec.ts`

| `skippedPeriod` | `true` ถ้าข้ามเพราะงวดนี้มีข้อมูลแล้ว | แยกให้ออกจาก "ไม่มีข้อมูลต้นทาง" |
| `existingRowCount` | จำนวนแถวที่มีอยู่แล้วในงวดนั้น | 🔴 **> 0 แต่น้อยผิดปกติ = รอบก่อนล้มกลางคัน ต้อง alert** |
| `sourceCount` | แถวที่วิวส่งมา (ก่อน dedup) | ต้นทางส่งครบไหม · เทียบงวดก่อนได้ |
| `deduplicatedCount` | แถวที่ถูกตัดจาก `DISTINCT` | ต้นทางส่งซ้ำมากผิดปกติหรือไม่ |
| `unmappedBrandCount` | แถวที่ **map ชื่อแบรนด์เข้า master ไม่ได้** (`brand_code = NULL`) | 🔴 **> 0 ต้อง alert** — master ตามไม่ทัน ALLMAP · **แถวยังถูกเก็บไว้ ไม่ได้ทิ้ง** |
| `noStoreCodeCount` | แถวที่ `COMPET_ID` ว่าง | 🔴 กระทบการกันซ้ำโดยตรง (ดูหัวข้อ 10) |
| `insertedCount` | แถวที่ insert สำเร็จ | ดูสมการด้านล่าง |
| `durationMs` | เวลาที่ใช้ทั้ง job | จับ performance ที่ถดถอย |

**สมการที่ต้องเป็นจริงเสมอ** (ใส่เป็น assertion ท้าย job ได้เลย):

```
sourceCount − deduplicatedCount  =  insertedCount
```

> ⚠️ **`unmappedBrandCount` ไม่หักออกจากสมการ** เพราะแถวที่ map แบรนด์ไม่ได้ **ยังถูก insert** (โดย `brand_code = NULL`)
> เป็นตัวนับเพื่อ alert เท่านั้น ไม่ใช่แถวที่ถูกทิ้ง

> ระบบเดิมมี reconcile อยู่แล้ว (`totalRecordInsert == impactCompetitorList.size()`) แต่ **ไม่มีช่องให้ reject รายแถว**
> ถ้าระบบใหม่เพิ่มการ reject (ข้อ 🔴 B) ต้องแก้สมการเป็นแบบข้างบน ไม่ใช่เทียบสองตัวตรง ๆ

### เมลแจ้งผล ≠ ผลของ job

เหมือน Job 2 — **ผลของ job อยู่ที่ exit code เท่านั้น** เมลกับ log เป็นข้อมูลประกอบ

> ✅ **จุดที่ Job 3 ทำดีกว่า Job 2** — ผู้รับอีเมลมาจาก `config.getMailTo()` (`SendMailUtil.java:127`)
> ไม่ได้ hardcode ไว้ในโค้ดแบบ Job 2 · **ระบบใหม่คงพฤติกรรมนี้ไว้** และย้ายไปใช้ `mas_param` / `email_template` ของระบบเดิม
