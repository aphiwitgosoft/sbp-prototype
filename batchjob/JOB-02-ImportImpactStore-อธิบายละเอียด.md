## 3. ภาพรวมการทำงาน 5 ขั้น

```
① ดึงข้อมูลจาก ALLMAP          → คู่ร้านทั้งหมดของงวดนั้น (SQL Server ของทีมอื่น)
        ↓
② กันซ้ำกับของที่มีอยู่แล้ว     → เอาเฉพาะคู่ที่ยัง "ไม่เคยรับเข้ามา" และ "ไม่ได้อยู่ในรอบชดเชยที่เปิดค้างอยู่"
        ↓
③ บันทึกเป็นแถวใหม่            → verify_status = 'W' (รอตรวจ) ทุกแถว
        ↓
   ─────────── ตั้งแต่ขั้นนี้ไป ทำกับแถว W "ทั้งตาราง" ไม่ใช่แค่แถวที่เพิ่ง insert ───────────
        ↓
④ เติมข้อมูลประกอบ             → นิติบุคคล + วันเริ่ม/ยกเลิกสัญญา SBP (join จากระบบเดิม)
                                 ⚠️ ส่วน "ประเภทร้าน" แถวของ job นี้ใช้ค่าจาก ALLMAP ไม่ได้เอาจาก master
        ↓
⑤ ตัดสินด้วยกฎธุรกิจ           → เปลี่ยน 'W' เป็น 'N' (ตัดทิ้ง) หรือ 'P' (ไปต่อ)
```

### 🔴 เรื่องที่เข้าใจผิดกันบ่อยที่สุด — ขั้น ④ กับ ⑤ เป็น "การกวาด" ไม่ใช่ "ประมวลผลรอบนี้"

SQL ทั้งสามคำสั่งของขั้น ④–⑤ มีเงื่อนไข **`WHERE flag_verify = 'W'` เพียงอย่างเดียว**
**ไม่มี `year` · ไม่มี `month` · ไม่มี run id** (`ImportStoreJdbc.java` บรรทัด 289 · 352 · 388)

แปลว่าทุกครั้งที่ Job 2 รัน มัน **กวาดแถวที่ยังเป็น `W` ทั้งตาราง** — รวมถึง

- แถวของ **งวดเก่า** ที่ค้างมาจากการรันครั้งก่อน ๆ
- แถวที่ **ไม่ได้มาจาก ALLMAP** เช่นแถวที่คีย์เข้ามาจาก Franchise Statement (`create_by = 'STA'`)
  ผ่านหน้าจอ (`ManageCompensateController` → `importImpactStoreExtra`) ซึ่งก็ insert เข้ามาเป็น `W` เหมือนกัน

**พฤติกรรมนี้อธิบายกฎ 2 ข้อที่ดูแปลก ๆ ได้ทันที**

| กฎ | ทำไมถึงต้องมี |
|---|---|
| **N5** — ตัดทิ้งแถวที่เก่ากว่า 12 เดือน | ถ้าไม่มีข้อนี้ แถว `W` ที่ไม่เข้าเกณฑ์สักทีจะ**สะสมค้างในตารางตลอดไป** และถูกกวาดซ้ำทุกเดือน |
| **P2** — แถว `STA` ผ่านทันที | เพราะการกวาดไปโดนแถว `STA` ด้วย ต้องมีทางให้มันจบ ไม่งั้นจะค้างเป็น `W` ตลอด |

และมี **guard สำคัญที่คู่กัน**: คำสั่งตัดทิ้ง (`N`) มีเงื่อนไข `'ALM' IN (create_by, update_by)` ครอบไว้
→ **แถว `STA` ไม่มีวันถูกตัดทิ้งโดย job นี้** มีแต่ทางเดียวคือถูกเลื่อนเป็น `P` ตามกฎ P2

> 💡 สรุปให้จำง่าย: **Job 2 = "รับของใหม่เข้ามา แล้วเคลียร์ของค้างทั้งตารางให้จบ"**
> ไม่ใช่ "ประมวลผลเฉพาะของที่เพิ่งรับเข้ามา"

> ⚠️ **ขั้น ③–⑤ ต้องอยู่ใน transaction เดียวกัน** — โค้ดเดิมทำแบบนี้ (`TransactionTemplate` + savepoint)
> ถ้าแยก transaction แล้วพังกลางทาง จะเหลือแถวค้างสถานะ `W` ที่ไม่มีใครมาตัดสินต่อ

## 4. ขั้นที่ ① — ดึงข้อมูลจาก ALLMAP

### รับอะไรมาบ้าง

อ่านจากวิว **`allmapssa.SEVEN_IMPACT_VIEW`** (SQL Server ของทีม ALLMAP — คนละฐานกับเรา)

| ข้อมูลที่ได้ | ความหมาย |
|---|---|
| `STORECODE_I` · `NAME_I` · `ZONE_I` · `SUBZONE_I` · `BRANCHTYPE_I` · `OPENDATE_I` | ร้าน **I** = **Impacted** = ร้าน SP ที่ถูกกระทบ |
| `STORECODE_N` · `NAME_N` · `ZONE_N` · `SUBZONE_N` · `BRANCHTYPE_N` · `OPENDATE_N` | ร้าน **N** = **New** = ร้านที่เปิดใหม่แล้วไปกระทบเขา |
| `DISTANCE` · `DISTANCE_UNIT` | ระยะห่างจริงระหว่างสองร้าน |
| `RADIUS` · `RADIUS_UNIT` | รัศมีเกณฑ์ที่ ALLMAP ใช้ตัดสิน |
| `URL_EMBEDDED` | ลิงก์แผนที่ที่ฝังดูได้ |
| `PERIOD_YEAR` · `PERIOD_MONTH` | งวดที่กระทบ |

> 💡 **จำง่าย ๆ:** ลงท้าย `_I` คือ **ร้านที่เดือดร้อน** · ลงท้าย `_N` คือ **ร้านที่ไปทำให้เดือดร้อน**

### กันข้อมูลซ้ำจากต้นทาง

ALLMAP อาจส่งคู่เดิมมาซ้ำหลายแถว โค้ดเดิมจึงใช้

```sql
ROW_NUMBER() OVER (PARTITION BY STORECODE_I, STORECODE_N, PERIOD_YEAR, PERIOD_MONTH
                   ORDER BY PERIOD_YEAR, PERIOD_MONTH) = 1
```

แปลว่า **1 คู่ (ร้านถูกกระทบ + ร้านเปิดใหม่ + งวด) เอาแค่แถวเดียว**

### 🔴 แต่ "แถวเดียว" นั้นคือแถวไหน — ตอนนี้ตอบไม่ได้

`ORDER BY PERIOD_YEAR, PERIOD_MONTH` **ใช้คอลัมน์ที่อยู่ใน `PARTITION BY` อยู่แล้ว**
ทุกแถวในกลุ่มจึงมีค่าเรียงเท่ากันหมด → **SQL Server เลือกแถวไหนก็ได้** (non-deterministic)

**ปกติไม่มีใครสังเกต** เพราะแถวซ้ำส่วนใหญ่เหมือนกันทุกค่า **แต่ถ้าค่าต่างกันเมื่อไรจะเป็นปัญหาจริง**:

| ค่าที่อาจต่างกันในกลุ่มเดียวกัน | ผลถ้าเลือกผิดแถว |
|---|---|
| `DISTANCE` / `DISTANCE_UNIT` | ระยะทางที่บันทึกต่างกัน — กระทบการตรวจสอบย้อนหลัง |
| `URL_EMBEDDED` | ลิงก์แผนที่คนละอัน (ดูข้อค้างในหัวข้อ 9) |
| `BRANCHTYPE_I` / `BRANCHTYPE_N` | ⚠️ **เปลี่ยนผล `P`/`N` ได้** เพราะกฎ N1 · N2 · P1 ตัดสินจาก `branchtype` |
| `RADIUS` / `ZONE` / ชื่อร้าน | ข้อมูลประกอบไม่ตรงกัน |

> ✅ **ระบบใหม่ต้องกำหนด tie-breaker ที่ deterministic** — รันซ้ำด้วยข้อมูลชุดเดิมต้องได้ผลเดิมเสมอ
> ข้อเสนอเพื่อใช้คุยกัน (เรียงตามลำดับ): **`DISTANCE` น้อยสุด** (ใกล้สุด = เคสที่กระทบจริงที่สุด) →
> ถ้ายังเท่ากันใช้ **`URL_EMBEDDED` ที่ไม่ว่าง** → สุดท้ายใช้คอลัมน์คีย์ที่มีค่าคงที่เรียง `ASC`
> **และต้องนับ/log ว่ามีกี่กลุ่มที่แถวซ้ำมีค่าไม่ตรงกัน** — ถ้าเจอบ่อยแปลว่าต้นทางมีปัญหา ต้องแจ้ง ALLMAP

### 🔴 หน่วยของระยะทาง — ต้องกำหนดกติกาแปลง

ระบบเดิม **เก็บทั้ง `DISTANCE` และ `DISTANCE_UNIT` ตามที่ ALLMAP ส่งมา ไม่เคยแปลงเลย**
(`ImportStoreMapper` อ่านทั้งคู่ · `ImportImpactStoreBatch` เขียนทั้งคู่ · ไม่มีโค้ดไหนอ่าน `DISTANCE_UNIT` มาคำนวณ)

**แต่ตารางใหม่มีคอลัมน์เดียวคือ `distance_km NUMERIC(8,3)`** — ไม่มีที่เก็บหน่วย
แปลว่า **Job 2 ต้องแปลงให้เป็นกิโลเมตรก่อนเขียน** และต้องมีกติกาครบทุกกรณี

✅ **profile ฐานจริงแล้ว 2026-09-12** — `DISTANCE_UNIT` ที่ ALLMAP ส่งมามี **ค่าเดียวเท่านั้นคือ `กิโลเมตร`**
(ภาษาไทย · 23,127 แถวของ `CREATE_BY = 'ALM'` ทั้งหมด) **ไม่เคยส่ง `KM`/`M` ภาษาอังกฤษเลย**
และคอลัมน์เดิมเป็น `NUMBER(3,2)` ค่าจริงอยู่ในช่วง **0.03–1.52 กม.** = เก็บเป็นกิโลเมตรอยู่แล้ว

| `DISTANCE_UNIT` ที่ได้รับ | ทำอย่างไร | เจอจริงกี่แถว |
|---|---|---|
| **`กิโลเมตร`** | ใช้ค่าตรง ๆ | **23,127** ← ค่าเดียวที่ ALLMAP ส่งจริง |
| `KM` · `km` · `กม.` | ใช้ค่าตรง ๆ (**เทียบแบบไม่สนตัวพิมพ์และตัดช่องว่าง**) | 0 — รับไว้เผื่อต้นทางเปลี่ยน |
| `M` · `m` · `เมตร` | หารด้วย 1,000 | 0 — รับไว้เผื่อต้นทางเปลี่ยน |
| **`NULL` / ว่าง** | **กันแถวไว้ ไม่เดา** (ตัดสินแล้ว) | 3,137 — ทั้งหมดเป็นแถว `CREATE_BY = 'STA'` ที่มี `DISTANCE = 0` **ซึ่ง Job 2 ไม่ได้สร้าง** จึงไม่กระทบ |
| **ค่าที่ไม่รู้จัก** | **ห้ามเดา** — log ค่าที่เจอแล้วกันแถวนั้นไว้ | 0 |

> ⚠️ **แปลงหน่วยผิดไป 1,000 เท่า จะทำให้ร้านที่อยู่ 800 เมตรกลายเป็น 800 กม.**
> รัศมีที่ใช้ตัดสินคือ **1 กม. (กทม./ปริมณฑล) · 2 กม. (ต่างจังหวัด)** — ผิดหน่วยแล้วคัดออกหมดทั้งงวดโดยไม่มีใครรู้
> **ต้องมี sanity check**: `distance_km` ที่แปลงแล้วต้องอยู่ในช่วงที่สมเหตุสมผล (เช่น `0 < d <= 50`) ถ้าหลุดช่วงให้ log + กันแถวไว้

### งวดที่ดึง — ค่าตั้งต้นคือ "เดือนที่แล้ว"

โค้ดเดิม: `modifyDateToString(new Date(), -1, "yyyy")` และ `"MM"` → **ถอยหลัง 1 เดือนจากวันที่รัน**
รันวันที่ 7 ก.ค. จึงดึงข้อมูลของงวด **มิถุนายน**

### Argument ที่รับได้

รูปแบบ `โซน|ปี|เดือน` เช่น `ALL|2026|06` หรือ `BN,BS,BW|2026|06`

| ตำแหน่ง | ความหมาย | ไม่ระบุแล้วเป็นอะไร |
|---|---|---|
| 1 | รายชื่อโซนคั่นด้วย comma · ใส่ `ALL` = ทุกโซน | ทุกโซน |
| 2 | ปี | ปีของเดือนที่แล้ว |
| 3 | เดือน | เดือนที่แล้ว |

### 🔴 พ.ศ. หรือ ค.ศ. — โค้ดเดิมขัดแย้งกันเอง ต้องยืนยันด้วยข้อมูลจริง

**ค่าตั้งต้นในโค้ดให้ ค.ศ.** — `Calendar.getInstance(Locale.US)` + `modifyDateToString(..., "yyyy", Locale.US)`
`Locale.US` ใช้ปฏิทิน Gregorian จึงได้ `2026` **ไม่ใช่ `2569`**

**แต่ตัวอย่าง argument ในเอกสาร/ผังของทีมคือ `2569|06`** (พ.ศ.) และไม่มีโค้ดตรงไหนแปลงเลย —
ค่าถูกส่งเข้า `WHERE PERIOD_YEAR = ?` ตรง ๆ · **ถ้าตัวอย่างนั้นถูก** ก็แปลว่า `PERIOD_YEAR` เก็บ พ.ศ.
และการรันแบบไม่ใส่ argument จะ **query ด้วย ค.ศ. แล้วไม่เจอข้อมูลเลย** เงียบ ๆ

## 5. ขั้นที่ ② — กันซ้ำ (เคสสำคัญที่สุดของ job นี้)

คู่ร้านที่ ALLMAP ส่งมา **ไม่ได้เอาเข้าทั้งหมด** ต้องเช็คก่อนว่าเข้าเงื่อนไขข้อใดข้อหนึ่งนี้หรือไม่

โค้ดเดิมเรียกรายการที่ **ต้องไม่รับเข้า** ว่า `impactStoreFranchiseList` (มาจาก `getImpactStoreFranchise`) แล้วเทียบด้วย `checkImpactStoreAllMapInFranchise()` ซึ่งเทียบครบ 4 ค่า: `storecode_i` + `storecode_n` + `year` + `month`

### รายการที่ต้องกันออก มาจาก 2 เงื่อนไข (เชื่อมด้วย OR)

| # | เงื่อนไข | ภาษาคน |
|---|---|---|
| **A** | มีแถวเดิมของ **งวดเดียวกัน** อยู่แล้ว (`month` + `year` ตรง) | คู่นี้นำเข้าไปแล้วในรอบนี้ — รันซ้ำก็ไม่เกิดแถวซ้ำ |
| **B** | ร้านนี้ **มีรอบชดเชยที่เปิดค้างอยู่** และงวดที่กำลังนำเข้า **อยู่ในช่วงของรอบนั้น** | ร้านนี้กำลังอยู่ระหว่างได้รับการชดเชยอยู่แล้ว ไม่ต้องเปิดเรื่องซ้อน |

**เงื่อนไข B ละเอียดขึ้น** (จาก SQL เดิม) — นับว่า "อยู่ในรอบ" เมื่อ

```
รอบนั้น flag_action อยู่ใน ('Y','W')                     ← รอบที่ยังเปิดหรือรอตรวจ
และ งวดที่นำเข้า  อยู่ระหว่าง  start_compensate (ปี+เดือน)
                        ถึง  last_compensate (ปี+เดือน)
                             ── ยกเว้น! ถ้าเดือนที่แล้วเท่ากับ last_compensate หรือ last_compensate+1
                                ให้ขยายเพดานเป็น "เดือนที่แล้ว" แทน
```

> 🔍 **ทำไมต้องมีข้อยกเว้นนั้น** — เพื่อให้รอบที่กำลังจะครบกำหนด **ต่ออายุได้อีก 1 เดือน**
> ถ้าไม่มีบรรทัดนี้ เดือนสุดท้ายของรอบจะหลุดออกจากการกันซ้ำ แล้วเกิดรอบใหม่ซ้อนทับรอบเดิมทันที

และมีตัวกรองพื้นฐานอีกชั้น: `fis.flag_verify != 'N'` — **แถวที่เคยถูกตัดทิ้งไปแล้ว ไม่นับเป็นตัวกันซ้ำ** (เปิดโอกาสให้คู่นั้นถูกพิจารณาใหม่ได้)

> 🔴 **แต่บน DDL ใหม่ทำแบบนี้ไม่ได้** — `uq_impact_store_pair UNIQUE (impacted_store_code, new_store_code, impact_month)` จะปฏิเสธการ insert คู่เดิมของงวดเดิม แม้แถวเดิมจะเป็น `N` แล้วก็ตาม
> ระบบเดิมทำได้เพราะ **ไม่มี UNIQUE บนสามคอลัมน์นี้** (เป็น INDEX ธรรมดา) — **ต้องเลือก contract ก่อนเขียนโค้ด ดูหัวข้อ 9**

### ⚠️ กับดักที่ต้องรู้ก่อนเขียนโค้ด

โค้ดเดิมมีเมธอด `checkImpactStoreAllMapInFranchise` ที่ **คืนค่าแบบสับสนมาก**:

```java
if (ตรงกันทั้ง 4 ค่า) return false;   // เจอในรายการกัน → คืน false
return true;                          // ไม่เจอ → คืน true
```

แล้วฝั่งเรียกใช้กลับเขียนว่า

```java
if (!checkImpactStoreAllMapInFranchise(...)) updateList.add(...);  // เจอ → เข้า updateList
else insertList.add(...);                                          // ไม่เจอ → เข้า insertList
```

และท้ายที่สุด **`updateList` ไม่ถูกใช้งานเลย** — `manageImpactStore()` รับแต่ `insertList`

**สรุปสำหรับคนเขียนใหม่:** ตรรกะจริงคือ **"คู่ไหนอยู่ในรายการกัน → ทิ้งไปเฉย ๆ · คู่ไหนไม่อยู่ → insert"**
ไม่ต้องทำ `updateList` ตามของเดิม (เป็นซากที่ไม่ได้ใช้) แต่ **ควรนับจำนวนที่ถูกกันออกไว้ใน log** เพื่อให้ตรวจสอบย้อนได้

## 7. ขั้นที่ ④ — เติมข้อมูลประกอบ

แถวที่เป็น `W` มีแต่ข้อมูลจาก ALLMAP ซึ่ง **ยังไม่พอสำหรับตัดสิน** ต้องไปเติมข้อมูลเพิ่ม

> ⚠️ **ขั้นนี้ทำกับแถว `W` ทั้งตาราง ไม่ใช่แค่แถวที่เพิ่ง insert** — `where a.flag_verify = 'W'` ไม่มีเงื่อนไขงวด
> (ดูหัวข้อ 3) · แถวเก่าที่ค้างจากงวดก่อน ๆ จะถูกเติมข้อมูล**ใหม่ทับของเดิม**ทุกครั้งที่ job รัน

### 🔴 กติกาที่พลาดง่ายที่สุด — ไม่ใช่ทุกฟิลด์ที่เอามาจาก master

โค้ดเดิมใช้ `decode()` แยกตาม **`create_by`** ว่าจะเอาค่าจากไหน:

```sql
decode(fis.create_by, 'STA', ms_i.status_type, fis.branchtype_i) as branchtype_i
--                     ↑ ถ้าเป็น STA เอาจาก mas_store    ↑ ไม่ใช่ STA (= ALM) คงค่าเดิมจาก ALLMAP
```

**Job 2 ตั้ง `create_by = 'ALM'` เสมอ** → แถวที่ job นี้สร้าง **ใช้ค่าจาก ALLMAP ทั้งหมด ไม่ได้เอาจาก `mas_store`**

| ฟิลด์ | แถวของ Job 2 (`ALM`) | แถวที่มาจาก Franchise Statement (`STA`) |
|---|---|---|
| `name_i` / `name_n` | **ค่าจาก ALLMAP** | `mas_store.branch_name` |
| `opendate_i` / `opendate_n` | **ค่าจาก ALLMAP** | `mas_store.open_date` |
| `zone_i` / `zone_n` | **ค่าจาก ALLMAP** | `mas_store.region` |
| **`branchtype_i` / `branchtype_n`** | **ค่าจาก ALLMAP** ⚠️ | `mas_store.status_type` |

ส่วนอีก 2 กลุ่มนี้ **มาจากระบบเดิมเสมอ ไม่ว่า `create_by` เป็นอะไร** (ไม่มี `decode` ครอบ):

| กลุ่มข้อมูล | เอามาจากไหน | เอาไปทำอะไร |
|---|---|---|
| **นิติบุคคล** (`juristic_id` · `juristic_name`) | `fr_store` → `juristic` | ใช้เทียบว่าเจ้าของเดียวกันหรือไม่ (กฎ N3) |
| **วันเริ่ม/ยกเลิกสัญญา SBP** (`start_date` · `cancel_date` · `cancel_type`) | `fr_store` | ใช้ตรวจว่าสัญญายังมีผลในงวดนั้นไหม (กฎ N4) |

> ⚠️ **ทำไมเรื่องนี้สำคัญมาก** — กฎ **N1 · N2 · P1** ตัดสินจาก `branchtype` ทั้งหมด
> ถ้าระบบใหม่เปลี่ยนไปอ่าน `mas_store.status_type` แทนค่าจาก ALLMAP **ผลลัพธ์ P/N อาจต่างจากระบบเดิม**
> เพราะ ALLMAP เป็นระบบของทีมอื่นและค่าที่ส่งมาคือ **ภาพ ณ เวลาที่ดึงข้อมูล** ซึ่งอาจไม่ตรงกับ master วันนี้
> (เช่น ร้านเปลี่ยนประเภทหลังจากงวดนั้นไปแล้ว) — **ต้องเลือกทางก่อนเขียนโค้ด ดูหัวข้อ 12**

### 🔴 กับดักซ้อน — `INNER JOIN` ทำให้ค่าจาก ALLMAP ถูกลบทิ้ง

`decode()` ข้างบนจะรักษาค่า ALLMAP ไว้ได้ **ก็ต่อเมื่อ subquery คืนแถวออกมา**
แต่ SQL จริงใช้ **`INNER JOIN mas_store`** ทั้งฝั่ง `_i` และ `_n`:

```sql
inner join mas_store ms_i on ms_i.branch_id = fis.storecode_i   -- ImportStoreJdbc.java:241
inner join mas_store ms_n on ms_n.branch_id = fis.storecode_n   -- ImportStoreJdbc.java:264
```

**ถ้าร้านใดร้านหนึ่งไม่มีใน `mas_store`** → subquery ไม่คืนแถวเลย → คำสั่ง `UPDATE ... SET (คอลัมน์ชุดใหญ่) = (subquery)`
จะเซ็ต **ทุกคอลัมน์ในชุดนั้นเป็น NULL** รวมถึง `branchtype_i` ที่ `decode()` ตั้งใจจะคงไว้

⚠️ **นี่คือการสูญเสียข้อมูล ไม่ใช่แค่ "เติมไม่ได้"** — ค่าที่ ALLMAP ส่งมาถูกทับหายไปถาวร
และเมื่อ `branchtype` เป็น NULL แถวนั้นจะ **ตกร่อง ค้างเป็น `W` ตลอดไป** (ดูหัวข้อ 8)

> ✅ **ระบบใหม่ต้องใช้ `LEFT JOIN`** และเขียนเงื่อนไขให้ **คงค่าเดิมไว้เมื่อหา master ไม่เจอ**
> (เช่น `coalesce(ms_i.status_type, fis.branchtype_i)` หรือแยก UPDATE รายกลุ่มคอลัมน์)

### วิธีเลือกสัญญาที่ถูกต้อง (สำคัญ — ร้านหนึ่งร้านมีหลายสัญญาได้)

โค้ดเดิมใช้

```sql
dense_rank() OVER (PARTITION BY store_id, month, year
                   ORDER BY start_date DESC, cancel_type, order_id DESC) = 1
```

พร้อมเงื่อนไขคัดกรอง

- `status != 'D'` — ตัดสัญญาที่ถูกลบ
- `store_id != '00000'` — ตัดรหัสร้านว่าง
- `cancel_type is not null`
- `start_date <= วันสุดท้ายของงวด` — สัญญาต้องเริ่มก่อนหรือภายในงวด
- `cancel_date >= วันแรกของงวด` (ถ้า `cancel_date` ว่างให้ถือเป็น `01/4000` = ยังไม่ยกเลิก)

แปลเป็นภาษาคน: **"เอาสัญญาที่ยังมีผลอยู่ในงวดนั้น และถ้ามีหลายฉบับให้เอาฉบับที่เริ่มล่าสุด"**

### 🔴 ข้อควรระวังใหญ่ที่สุดของขั้นนี้ในระบบใหม่

ตารางใหม่ **`sgi_fgi_impact_stores` ไม่มีคอลัมน์เหล่านี้เลย** — ไม่มี `branchtype_i` · `juristic_name_i` · `sbp_start_date_i` · `sbp_cancel_date_i` · `sbp_cancel_type_i`
(เป็นไปตามหลักการที่ตกลงกันว่า **ห้ามเก็บ master ซ้ำ** — ดูช่องว่าง G3/G4 ในเอกสาร LLDD)

**สำหรับนิติบุคคลและสัญญา SBP (กฎ N3 · N4) ไม่มีปัญหา** — ระบบเดิมก็ join เอาจาก `fr_store`/`juristic` อยู่แล้ว
ระบบใหม่แค่เปลี่ยนจาก "UPDATE เติมค่าก่อนแล้วค่อยตัดสิน (2 ขั้น)" เป็น **"JOIN แล้วตัดสินในคำสั่งเดียว"** — ผลลัพธ์เท่ากัน

**แต่สำหรับ `branchtype` เป็นคนละเรื่อง** ⚠️
ค่าที่ระบบเดิมใช้ตัดสินคือ **ค่าจาก ALLMAP** (ดูหัวข้อ 7) ซึ่ง **สร้างขึ้นใหม่จาก master ไม่ได้**
ถ้าระบบใหม่ join `mas_store` มาแทน = **เปลี่ยนพฤติกรรมทางธุรกิจ** ไม่ใช่แค่ย้ายที่เก็บ

| ทางเลือก | ต้องทำอะไร | ผล |
|---|---|---|
| **ก. รักษาพฤติกรรมเดิม** | เพิ่ม 2 คอลัมน์ใน `sgi_fgi_impact_stores` เก็บ `branchtype` ของทั้งสองร้าน **ตามที่ ALLMAP ส่งมา** | ผล P/N ตรงกับระบบเดิม 100% · แลกกับการมีคอลัมน์เพิ่ม (ไม่ใช่ master ซ้ำ — เป็น **snapshot ณ เวลานำเข้า**) |
| **ข. ใช้ master ปัจจุบัน** | join `mas_store.status_type` ตอนตัดสิน ไม่เก็บอะไรเพิ่ม | โครงสะอาดกว่า · แต่ **ผล P/N อาจต่างจากระบบเดิม** และ**ตรวจสอบย้อนหลังไม่ได้** ว่าตอนนั้นตัดสินด้วยค่าอะไร |

> 📌 ข้อสังเกตประกอบการตัดสินใจ: หลักการ "ห้ามเก็บ master ซ้ำ" มีไว้กัน**ข้อมูลอ้างอิงที่เปลี่ยนตาม master** (ชื่อร้าน ที่อยู่)
> แต่ค่าที่ใช้**ตัดสินแล้วบันทึกผล** เป็นคนละประเภท — ปกติควรเก็บ snapshot ไว้ (แบบเดียวกับ `approver_snapshot` ในเอกสาร)
> **แต่นี่เป็นการตัดสินใจเชิงออกแบบ ต้องให้เจ้าของงานเคาะ ไม่ใช่ตัดสินเองในเอกสารนี้**

**ที่แน่นอนไม่ว่าจะเลือกทางไหน:** **ห้ามเขียนอะไรลงตารางของระบบเดิม** — `mas_store` · `fr_store` · `juristic` อ่านอย่างเดียว

## 8. ขั้นที่ ⑤ — กฎตัดสิน (ใจความสำคัญที่สุดของทั้ง job)

หลังเติมข้อมูลแล้ว แถวที่ยังเป็น `W` **ทั้งตาราง (ทุกงวด ทุกแหล่งที่มา)** จะถูกตัดสินเป็น `N` (ตัดทิ้ง) หรือ `P` (ไปต่อ)
โค้ดเดิมรัน **2 คำสั่งเรียงกัน**: ตัดทิ้งก่อน แล้วค่อยเลื่อนที่เหลือให้ไปต่อ

### กติกาประเภทร้านที่ต้องรู้ก่อน

| กลุ่ม | รหัสประเภทร้าน | ความหมาย |
|---|---|---|
| **ร้าน SP ที่เข้าข่ายชดเชย** | `B` · `FAM` · `FB1` · `FB2` · `FC1` · `FVB` · `FVC` | ร้านที่อยู่ในโครงการ |
| **กรณีพิเศษ** | `FPT1` **และ** `sbp_cancel_type = '06'` | นับเข้าข่ายเฉพาะเมื่อ cancel_type เป็น 06 เท่านั้น |
| **ร้านบริษัท** | `F` | ถ้า**ร้านที่เปิดใหม่**เป็นประเภทนี้ = ไม่ชดเชย |

### 8.1 กฎ "ตัดทิ้ง" → `verify_status = 'N'`

ทำงานกับแถวที่ `verify_status = 'W'` **ทุกงวด** และ `'ALM' IN (created_by, updated_by)`
→ **แถวที่มาจาก `STA` ไม่มีวันถูกตัดทิ้งด้วยกฎกลุ่มนี้**
ตัดทิ้งเมื่อเข้า**ข้อใดข้อหนึ่ง** (OR):

| # | เงื่อนไข | เหตุผลเชิงธุรกิจ |
|---|---|---|
| **N1** | ร้านถูกกระทบ **ไม่ได้อยู่ในกลุ่มร้าน SP** (`branchtype_i` ไม่อยู่ใน 8 รหัสข้างบน) | ไม่ใช่ร้านในโครงการ ไม่มีสิทธิ์ได้ชดเชย |
| **N2** | ร้านที่เปิดใหม่เป็น **ร้านบริษัท** (`branchtype_n = 'F'`) | บริษัทเปิดเอง ไม่ใช่กรณีที่ต้องชดเชยให้ SP |
| **N3** | **นิติบุคคลของสองร้านเหมือนกัน** (`juristic_name_n = juristic_name_i`) | **เจ้าของเดียวกัน** — เปิดร้านใหม่แข่งกับตัวเอง ไม่ชดเชย |
| **N4** | ร้าน SP **สัญญายังไม่เริ่ม หรือ ยกเลิกไปแล้ว** ณ งวดนั้น<br>(`sbp_start_date_i >= วันสุดท้ายของงวด` **หรือ** `งวด >= sbp_cancel_date_i`) | ยังไม่เป็น SP หรือพ้นสภาพไปแล้ว |
| **N5** | แถวนี้ **ถูกสร้างมานานเกิน 12 เดือน** (`sysdate > add_months(create_date, 12)`) | ค้างเกิน 1 ปีถือว่าหมดอายุ ไม่ต้องพิจารณาต่อ |

> ⚠️ **N3 ใช้ชื่อนิติบุคคลเทียบกัน ไม่ใช่รหัส** และมี `trim(nvl(..., 'ค่าเริ่มต้นคนละตัว'))` ครอบ
> ค่าเริ่มต้นของสองฝั่ง**จงใจให้ต่างกัน** (`'juristic_n'` กับ `'juristic_i'`) เพื่อว่า **ถ้าทั้งคู่เป็น NULL จะถือว่า "คนละเจ้าของ"** ไม่ใช่ "เจ้าของเดียวกัน"
> — จุดนี้พลาดง่ายมาก ถ้าเขียนใหม่แล้วใช้ค่าเริ่มต้นเดียวกันทั้งสองฝั่ง **ร้านที่ไม่มีข้อมูลนิติบุคคลจะถูกตัดทิ้งทั้งหมด**

### 8.2 กฎ "ไปต่อ" → `verify_status = 'P'`

ทำงานกับแถวที่ยังเป็น `W` **ทุกงวด** (ที่รอดจากกฎตัดทิ้ง) · ผ่านเมื่อเข้า**ข้อใดข้อหนึ่ง**:

| # | เงื่อนไข |
|---|---|
| **P1** | `created_by = 'ALM'` **และครบทุกข้อ**:<br>① `branchtype_i` อยู่ใน `B/FAM/FB1/FB2/FC1/FVB/FVC` **หรือ** (`FPT1` และ `cancel_type = '06'`)<br>② `branchtype_n != 'F'`<br>③ นิติบุคคล**ต่างกัน**<br>④ `sbp_start_date_i < วันสุดท้ายของงวด` **และ** `งวด < sbp_cancel_date_i` |
| **P2** | `created_by = 'STA'` — **ผ่านทันทีโดยไม่ต้องตรวจอะไรเลย** |

> 📌 **P2 คือเคสที่คนมักลืม** — แถวที่มาจาก **Franchise Statement (STA)** ถูกคีย์เข้ามาโดยคนหรือระบบอื่น
> (ผ่านเมธอด `importImpactStoreExtra` คนละทางกับ job นี้) ถือว่า**ผ่านการตรวจโดยมนุษย์มาแล้ว** จึงข้ามกฎทั้งหมด

### 🔴 แถวที่ "ตกร่อง" — ไม่เข้าทั้งกฎตัดทิ้งและกฎไปต่อ จึงค้างเป็น `W`

**ระบบเดิมปล่อยให้มีแถวค้าง `W` ได้จริง** และเป็นพฤติกรรมที่เกิดบ่อยกว่าที่คิด

เหตุผลอยู่ที่ **ตรรกะสามค่า (three-valued logic) ของ SQL** — เมื่อ `branchtype` เป็น `NULL`:

| เงื่อนไข | ผลเมื่อ `branchtype_i` เป็น NULL |
|---|---|
| DENY · `branchtype_i NOT IN (...)` | `NULL` — **ไม่ใช่ TRUE** จึงไม่ตัดทิ้ง |
| DENY · `branchtype_n IN ('F')` | `NULL` |
| DENY · นิติบุคคลเหมือนกัน | `FALSE` (เพราะ default สองฝั่งต่างกัน — ดูหัวข้อ 8.1) |
| DENY · เก่ากว่า 12 เดือน | `FALSE` (แถวเพิ่งสร้าง) |
| PASS · P1 ต้อง `branchtype_i IN (...)` | `NULL` — ไม่ผ่าน |
| PASS · P2 ต้อง `create_by = 'STA'` | `FALSE` (เป็น `ALM`) |

→ **ไม่มีคำสั่งไหนแตะแถวนี้เลย · ค้างเป็น `W` ต่อไป** จนกว่าจะครบ 12 เดือนแล้วโดนกฎ N5 เก็บกวาด

### สาเหตุที่ทำให้แถวตกร่อง — ✅ **วัดจากข้อมูลจริงแล้ว 2026-09-12**

เดิมหัวข้อนี้เป็นการ **ตั้งสมมติฐานจากการอ่านโค้ด** และสรุปว่า W1 ร้ายแรงที่สุด
พอ profile ฐาน Oracle จริง (`FGI_IMPACT_STORE_BK_20250515` · **3,064 แถวที่ค้าง `W`**) ปรากฏว่า**คนละเรื่อง**

| # | สาเหตุที่เคยเดาไว้ | จำนวนแถวจริงที่ค้าง `W` เพราะสาเหตุนี้ |
|---|---|---|
| **W1** | หาร้านใน `mas_store` ไม่เจอ → `branchtype` ถูกทับเป็น NULL | **0 แถว** ❌ ไม่ใช่สาเหตุเลย — `branchtype_i` ไม่เคยเป็น NULL ในแถวที่ค้าง `W` แม้แต่แถวเดียว |
| **W2** | ALLMAP ส่ง `BRANCHTYPE` ว่าง | **0 แถว** ❌ |
| **W3** | **ไม่มีสัญญาใน `fr_store` ที่คลุมงวดนั้น** | **2,684 แถว (87.6%)** 🔴 **สาเหตุจริงที่แท้จริง** |
| **W4** | รหัสประเภทร้านนอกชุดที่กฎรู้จัก | **0 แถว** ❌ |
| **W5** (ใหม่) | **`FPT1` ที่ `cancel_type` ไม่ใช่ `'06'`** | **382 แถว (12.5%)** 🔴 — ไม่เข้าทั้ง DENY และ PASS |

ประเภทร้านของแถวที่ค้าง `W` ทั้งหมด: `B` 2,680 · `FPT1` 382 · `FB2` 1 · `FC1` 1
(`B` อยู่ในชุดเข้าเกณฑ์อยู่แล้ว จึงค้างเพราะขาดสัญญา ไม่ใช่เพราะประเภทร้าน)

> ✅ **W1 ไม่ใช่ปัญหาในทางปฏิบัติ** — แต่โค้ดใหม่ก็ใช้ `LEFT JOIN` และไม่เขียนทับอะไรอยู่แล้ว
> จึงไม่ต้องแก้อะไรเพิ่ม ถือเป็นการกันไว้เฉย ๆ
>
> 🔴 **สิ่งที่ต้องแก้จริงคือ W3** — ร้านที่ **ไม่มีสัญญา SBP คลุมงวดนั้น** คิดเป็น 87.6% ของแถวที่ค้าง
> ทั้งกฎ DENY ข้อ N4 และกฎ PASS ข้อ P1④ ต่างอ้าง `sbp_start_date_i` / `sbp_cancel_date_i`
> เมื่อทั้งคู่เป็น NULL ทั้งสองกฎให้ผล NULL → ไม่มีคำสั่งไหนแตะแถวนั้น
> **นี่คือช่องว่างของกติกา ไม่ใช่บั๊กของการ join** — ต้องเคาะว่าร้านที่ไม่มีสัญญา SBP ควรเป็น `N` ทันที
> หรือค้าง `W` รอสัญญาเข้ามาทีหลัง (`DECISIONS` ข้อ 2.15)

### 🔴 ต้องกำหนดนโยบายให้ชัดก่อนเขียนโค้ด — แถวที่ข้อมูลไม่ครบจะทำอย่างไร

ระบบเดิม **ไม่มีนโยบาย** — ปล่อยค้างเงียบ ๆ ไม่มีใครรู้จนกว่าจะไปตายที่ job ถัดไป
ระบบใหม่ต้องเลือกหนึ่งทาง:

| ทาง | ทำอะไร | เหมาะเมื่อ |
|---|---|---|
| **ก. ทำให้ job ล้มเหลว** | เจอแถวที่ enrich ไม่ครบ → throw ทันที rollback ทั้งหมด | ถือว่าข้อมูลไม่ครบ = ผิดปกติร้ายแรง · ❌ เสี่ยงที่ร้านเดียวทำให้ทั้งงวดไม่เข้า |
| **ข. คงเป็น `W` + บันทึกเหตุผล** | เพิ่มคอลัมน์เก็บเหตุผล (เช่น `hold_reason`) แล้วให้รอบหน้ามาเก็บกวาด | ✅ ใกล้พฤติกรรมเดิมที่สุด และ**อธิบายได้**ว่าทำไมค้าง · ต้องแก้ DDL |
| **ค. ย้ายเข้า quarantine** | แยกตารางหรือ flag ต่างหากสำหรับแถวที่ข้อมูลไม่ครบ | โครงชัด · ❌ เพิ่มตาราง/ขั้นตอนที่ต้องมีคนดูแล |
| **ง. ตัดเป็น `N` ทันที** | ข้อมูลไม่ครบ = ไม่เข้าเกณฑ์ | ✅ ง่ายและไม่มีของค้าง · ❌ **ตัดทิ้งถาวร** ทั้งที่เดือนหน้า master อาจครบแล้ว (เข้าข้อขัดแย้ง UNIQUE ในหัวข้อ 9 อีกชั้น) |

### ตัวเลขที่ job ต้องรายงานทุกรอบ (ขั้นต่ำ)

ระบบเดิมรายงานแค่ "สำเร็จ/ล้มเหลว" ในอีเมล — **ตามไม่ได้ว่าเกิดอะไรขึ้นบ้าง**
ระบบใหม่ต้องเขียน structured log 1 บรรทัดตอนจบ (`BATCH_END`) พร้อมตัวเลขครบชุดนี้

| ชื่อ | นับอะไร | ตรวจอะไรได้ |
|---|---|---|
| `sourceCount` | แถวที่ ALLMAP ส่งมาทั้งหมด (ก่อน dedup) | ต้นทางส่งมาครบไหม · เทียบกับงวดก่อนได้ |
| `deduplicatedCount` | แถวที่ถูกตัดจากการกันซ้ำต้นทาง (`ROW_NUMBER`) | ต้นทางส่งซ้ำมากผิดปกติหรือไม่ |
| `skippedExistingCount` | แถวที่กันออกเพราะมีอยู่แล้ว (หัวข้อ 5) | รันซ้ำงวดเดิมควรเข้าช่องนี้เกือบทั้งหมด |
| `insertedCount` | แถวคู่ร้านที่ insert ใหม่จริง | **`source − deduplicated − skippedExisting` ต้องเท่ากับค่านี้** ถ้าไม่เท่าแปลว่ามีแถวหายไปเงียบ ๆ |
| `verifyPassCount` | ตัดสินเป็น `P` | สัดส่วน P/N ผิดปกติเทียบกับงวดก่อนไหม |
| `verifyDenyCount` | ตัดสินเป็น `N` | ↑ |
| `remainingWCount` | **ยังเป็น `W` หลัง job จบ** | 🔴 **> 0 ต้อง alert** — มีคู่ร้านที่ระบบตัดสินไม่ได้ (แยกตามสาเหตุ W1–W4 ถ้าทำได้) |
| `failedCount` | แถวที่ประมวลผลไม่ผ่าน (เช่น หน่วยระยะทางไม่รู้จัก) | ต้องเป็น 0 · ถ้าไม่ใช่ 0 ต้องมีรายละเอียดใน log |
| `durationMs` | เวลาที่ใช้ทั้ง job | จับ performance ที่ถดถอย |

**สมการที่ต้องเป็นจริงเสมอ** (ใส่เป็น assertion ท้าย job ได้เลย):

```
sourceCount − deduplicatedCount − skippedExistingCount  =  insertedCount
verifyPassCount + verifyDenyCount + remainingWCount     =  จำนวนแถว W ทั้งหมดที่กวาดในรอบนี้
```

- 🔴 **alert เมื่อ `remainingWCount > 0` หรือ `failedCount > 0`** — จะไม่มีใครรู้เลยถ้าไม่แจ้ง
- log รหัสร้านที่ค้างด้วย (จำกัดจำนวน เช่น 20 รายการแรก) เพื่อให้ตามแก้ที่ master ได้ทันที

### เมลแจ้งผลล้มเหลว ≠ job ล้มเหลว

| สถานการณ์ | ระบบเดิม | ระบบใหม่ต้องเป็น |
|---|---|---|
| งานสำเร็จ · ส่งเมลสำเร็จ | exit 0 | exit **0** |
| **งานสำเร็จ · แต่ส่งเมลไม่ได้** | `sendMailToAdmin` คืน `false` แล้ว **ไม่มีใครรับค่าไปใช้** | exit **0** (งานสำเร็จจริง) แต่ต้อง **log ระดับ ERROR + alert** ว่าส่งเมลไม่ได้ |
| **งานล้มเหลว · ส่งเมลสำเร็จ** | ส่งเมล FAIL แล้ว **exit 0** ⚠️ | exit **ไม่ใช่ 0** |
| **งานล้มเหลว · ส่งเมลไม่ได้ด้วย** | เงียบสนิท ⚠️⚠️ | exit **ไม่ใช่ 0** — scheduler เห็นแน่นอนแม้เมลไม่ถึง |

> **กติกาเดียว: ผลของ job อยู่ที่ exit code เท่านั้น** — เมลกับ log เป็นข้อมูลประกอบ
> การส่งเมลล้มเหลว **ห้ามทำให้ job ที่สำเร็จกลายเป็นล้มเหลว** และ **ห้ามทำให้ job ที่ล้มเหลวดูเหมือนสำเร็จ**

|---|---|---|---|---|---|

```sql
INSERT INTO sgi_fgi_impact_stores (

    -- verify_status · created_by · sales_request_status ปล่อยให้ DEFAULT ของ DDL ใส่ให้

ON CONFLICT (impacted_store_code, new_store_code, impact_month) DO NOTHING;
```

> 💡 **`UNIQUE (impacted_store_code, new_store_code, impact_month)` คือกลไกกันซ้ำชั้นสุดท้าย**
> ตรงกับ 4 ค่าที่โค้ดเดิมใช้เทียบใน `checkImpactStoreAllMapInFranchise` พอดี (รหัสร้าน 2 ตัว + งวด)
> → แม้ logic กันซ้ำในขั้น ② พลาด ฐานข้อมูลก็ยังกันให้อีกชั้น

### 🔴 ข้อขัดแย้งที่ยังไม่ได้ตัดสิน — UNIQUE ตัวนี้ปิดเคส "เคยเป็น N แล้วนำเข้าใหม่"

**ระบบเดิมทำได้ ระบบใหม่ทำไม่ได้** — ตรวจจากสคริปต์ schema จริงของระบบเดิม:

| | ระบบเดิม (`FGI_IMPACT_STORE`) | ระบบใหม่ (`sgi_fgi_impact_stores`) |
|---|---|---|
| PK | `IMPACT_STORE_ID` (sequence) | `id` (BIGSERIAL) |
| คู่ร้าน + งวด | **`IDX_FGI_IMPACT_STORE` เป็น INDEX ธรรมดา ไม่ใช่ UNIQUE** | **`uq_impact_store_pair` เป็น UNIQUE** |
| มีหลายแถวต่อ (ร้าน I + ร้าน N + งวด) ได้ไหม | **ได้** | **ไม่ได้** |

> หลักฐาน: `fcs_frn_stqa_schema_20260806.sql` บรรทัด 17494 — `CREATE INDEX` (ไม่มีคำว่า UNIQUE)
> ครอบ `STORECODE_I, STORECODE_N, BRANCHTYPE_I, BRANCHTYPE_N, MONTH, YEAR, FLAG_VERIFY, ...`

**ผลคือกลไกของระบบเดิมทำงานแบบนี้** — ตัวกันซ้ำในขั้น ② มีเงื่อนไข `fis.flag_verify != 'N'`
แปลว่า **แถวที่เป็น `N` ไม่นับเป็นตัวกัน** → ALLMAP ส่งคู่เดิมมาอีกก็ **insert แถวใหม่เป็น `W` เพิ่มได้**
โดยแถว `N` เดิมยังอยู่เป็นประวัติ · **บน DDL ใหม่ทำแบบนี้ไม่ได้** เพราะ UNIQUE จะปฏิเสธ

### สามทางที่เลือกได้ — ต้องเคาะก่อนเขียนโค้ด

| ทาง | ทำอะไร | ได้อะไร / เสียอะไร |
|---|---|---|
| **ก. reuse แถวเดิม แล้ว reset กลับ `W`** | เปลี่ยน `DO NOTHING` เป็น `DO UPDATE SET verify_status='W', updated_by='ALM', updated_at=now()` **เฉพาะเมื่อแถวเดิมเป็น `N`** (`WHERE ... verify_status = 'N'`) | ✅ ได้พฤติกรรมเดิม · คง UNIQUE ไว้ · ❌ **ประวัติหาย** — ไม่รู้ว่าเคยถูกตัดด้วยเหตุผลอะไร และ `created_at` เดิมถูกใช้โดยกฎ N5 (12 เดือน) จะเพี้ยน |
| **ข. ไม่อนุญาตให้นำเข้าใหม่** | คง `DO NOTHING` ตามที่เขียนไว้ | ✅ ง่ายที่สุด · โครงสะอาด · ❌ **เปลี่ยนพฤติกรรมธุรกิจ** — คู่ที่เคยถูกตัดเพราะข้อมูล master ยังไม่พร้อม (เช่นสัญญายังไม่ขึ้นระบบ) จะไม่มีโอกาสกลับมาอีกเลย |
| **ค. เพิ่มรอบ/ครั้งที่ลงใน key** | เพิ่มคอลัมน์ เช่น `attempt_no` แล้วเปลี่ยน UNIQUE เป็น `(impacted_store_code, new_store_code, impact_month, attempt_no)` | ✅ ได้ทั้งพฤติกรรมเดิมและเก็บประวัติครบ · ❌ ต้องแก้ DDL + ทุก query ที่ join คู่ร้านต้องรู้ว่าเอา attempt ไหน |

> 📌 **ข้อมูลประกอบการตัดสิน** — ถามว่า *"เคสนี้เกิดจริงบ่อยแค่ไหน"*
> เหตุที่คู่ร้านถูกตัดเป็น `N` แล้วควรกลับมาได้ มักเป็นเรื่อง **ข้อมูลใน master ยังไม่พร้อมตอนที่ job รัน**
> (สัญญา SBP ยังไม่ถูกคีย์ · นิติบุคคลยังว่าง) ซึ่งเดือนถัดไปข้อมูลอาจครบแล้ว
> แต่เนื่องจากขั้น ④–⑤ **กวาดแถว `W` ทั้งตารางอยู่แล้ว** (ดูหัวข้อ 3) เคสนี้จะครอบคลุมโดยอัตโนมัติ
> **เฉพาะกรณีที่แถวยังเป็น `W`** — พอถูกตัดเป็น `N` ไปแล้วเท่านั้นที่ต้องอาศัยการนำเข้าใหม่

### สรุปเป็น pseudocode

```
for แต่ละคู่ร้านที่ผ่านการกันซ้ำในขั้น ②:
    upsert sgi_impacted_stores(store_code = storecodeI)        -- DO NOTHING
    upsert sgi_impacted_stores(store_code = storecodeN)?       -- ⚠️ ดูหมายเหตุ
    processId = upsert sgi_fgi_impact_processes(...) RETURNING id
    insert   sgi_fgi_impact_stores(impact_process_id = processId, ...)  -- DO NOTHING
```

> ⚠️ **หมายเหตุเรื่องร้านเปิดใหม่ (`new_store_code`)** — คอลัมน์นี้ **ไม่มี FK** ไป `sgi_impacted_stores`
> (ดู DDL — มีแต่คอมเมนต์ว่า "master ของระบบเดิม") จึง **ไม่ต้อง upsert ร้าน N**
> เพราะร้านที่เปิดใหม่ไม่ใช่ร้าน SP ที่จะได้รับการชดเชย — เป็นแค่ต้นเหตุ

### ตารางระบบเดิมที่ **อ่านอย่างเดียว** (ห้ามเขียนเด็ดขาด)

### สี่ทางที่เลือกได้ — ต้องเคาะก่อนเขียนโค้ด

| ทาง | ทำอะไร | ได้อะไร / เสียอะไร |

> ถ้าตัดสินใจเก็บ snapshot ก็ควรตัดสินพร้อมกันทีเดียว

> ### 🔴 แก้ 2026-09-14 — ข้อ 3.6 · 3.7 · 3.10 เคยขัดกับหัวข้อ 8 ของเอกสารฉบับนี้เอง
>
> เดิมตารางนี้เขียนว่าทั้งสามเคสต้องเป็น **`N`** ซึ่งขัดกับผลวัดข้อมูลจริงในหัวข้อ 8:

> · 382 แถว = 12.5%) — ซึ่งหัวข้อ 8 สรุปเองว่า *"ช่องว่างของกติกา ไม่ใช่บั๊กของการ join"*
>

> → `sbp_start_date_i`/`sbp_cancel_date_i` เป็น NULL → ทั้ง DENY (N4) และ PASS (P1④)
> ให้ผล NULL → **ไม่มีคำสั่งไหนแตะแถวนั้น** จึงค้าง `W`
>
> **`DECISIONS` ข้อ 2.15 ยังไม่ปิด** — โค้ดทำทางเลือก **ข.** (คง `W` + `remainingWCount` + alert)

## 11. กับดักในโค้ดเดิม — สิ่งที่ **ห้ามลอกไป** ระบบใหม่

หัวข้อนี้ไม่ใช่กติกาธุรกิจ แต่เป็น**ข้อบกพร่องเชิงวิศวกรรมของโค้ดเดิม**ที่เจอตอนอ่านโค้ด
เขียนไว้เพราะคนที่พอร์ตไป NestJS มักจะ "ลอกโครงเดิม" มาโดยไม่รู้ว่าอันไหนเป็นบั๊ก

| # | กับดัก | ที่มาในโค้ดเดิม | ระบบใหม่ต้องทำอย่างไร |
|---|---|---|---|
| **L1** | **อ่านไฟล์ข้อความไม่ได้ แต่แจ้งว่า job สำเร็จ** | `main/ImportImpactStore.java:74–80` — `catch(IOException)` ตั้ง `JOB_STATUS_SUCCESS` แล้วใส่โน้ต `"Wanning IOException Please check file msgEN.properties"` | **`IOException` = ล้มเหลว** ห้ามรายงานเป็นสำเร็จ · ถ้าอ่าน resource ข้อความไม่ได้ให้ fail fast ตอน bootstrap ไม่ใช่กลางงาน |
| **L2** | **query ล้ม → DAO คืน `null` → NPE กลบต้นเหตุ** | `dao/jdbc/ImportStoreJdbc.java:55–58` — `catch(Exception)` log แล้ว `return null` · `service/ImpactStoreService.java:34,36` เรียก `.size()` ต่อทันที | **ให้ error โผล่ขึ้นมาตามจริง** — โยน exception ต่อ (หรือคืน `[]` เฉพาะกรณี "ไม่มีข้อมูล" ที่ต่างจาก "ต่อฐานไม่ได้") · ห้ามใช้ `null` แทนความล้มเหลว |
| **L3** | **จับ exception แล้วไม่กำหนด exit code** | `main/ImportImpactStore.java:81–88` — `catch(Exception)` ตั้ง `JOB_STATUS_FAIL` ส่งเมล แล้ว**หลุดออกจาก method ตามปกติ** ไม่ rethrow ไม่ `System.exit` | **process ต้องออกด้วย non-zero เมื่อ job ล้มเหลว** — ไม่งั้น **AWS Batch เห็นว่าสำเร็จ** ทั้งที่ล้ม · เมลไม่ใช่ช่องทางแจ้งความล้มเหลวของ scheduler |
| **L4** | **ต่อ `zone` เข้า SQL เป็นสตริง** | `dao/jdbc/ImportStoreJdbc.java:40–43` — `sql += " AND ZONE_I in ("+zoneStr+")"` (ค่าอื่นใช้ `?` แต่ zone ไม่ใช้) · zone มาจาก argument ของ job | **bind parameter เสมอ** + **whitelist ชุดโซนที่ยอมรับ** แล้ว reject ค่าที่ไม่อยู่ในชุด · เป็นช่อง SQL injection ที่รับค่าจากภายนอกได้จริง |
| **L5** | **transaction ซ้อนกันสองชั้น** | `service/ImpactStoreService.java:104–120` — อยู่ใน `TransactionTemplate.execute()` แล้ว**เขียนทับพารามิเตอร์ `status`** ด้วย `transactionManager.getTransaction(...)` ตัวใหม่ · สร้าง savepoint · `commit(status)` เอง | **ใช้ transaction ชั้นเดียว** (`DataSource.transaction()` / `QueryRunner` ของ TypeORM) · ปล่อยให้ framework จัดการ commit/rollback · **ห้ามคัดลอกโครงนี้** — ของเดิม commit ชั้นในไปแล้ว ชั้นนอกจึงคุมอะไรไม่ได้ และ `catch` ก็กลืน error ทิ้ง |
| **L6** | **credential + endpoint จริงฝังอยู่ใน source/config** | `jdbc.properties:46–48` (user/password/URL ของ ALLMAP · **prod**) · `Constant/FgiConstant.java:23` (`K2USER` = domain user + รหัสผ่าน) · endpoint K2 UAT/DEV สลับด้วยการ comment | **ใช้ Secrets Manager / env** ไม่มีความลับใน repo · 🔴 **credential ชุดเดิมถูกเปิดเผยใน source แล้ว ต้อง rotate** ไม่ใช่แค่ย้ายที่เก็บ |
| **L7** | **ผู้รับอีเมลถูก hardcode** | `main/ImportImpactStore.java:119–120` — `email.addTo("go-sbp@gosoft.co.th")` (และโหมดทดสอบสลับด้วย `Constant.IS_TEST` ในโค้ด) | **ผู้รับมาจาก config** — ระบบใหม่มี `email_template` + `mas_param` + `@gosoft-sbp/email-lib` อยู่แล้ว · เปลี่ยนผู้รับต้องไม่ต้อง build ใหม่ |

> ⚠️ **L1 + L3 รวมกันคือความเสี่ยงที่ร้ายที่สุดของ job นี้**
> ทั้งสองทางทำให้ **งานล้มเหลวแต่ scheduler เห็นเป็นสำเร็จ** — ไม่มีใครรู้จนกว่าจะไปตายที่ Job 4 หรือ Job 8
> ระบบใหม่ต้องยึดกติกาเดียว: **job ล้มเหลว = exit code ไม่ใช่ 0 เสมอ** · เมล/log เป็นข้อมูลประกอบ ไม่ใช่ตัวชี้ผล

> 📌 **ข้อ L6 อยู่นอกขอบเขตเอกสารนี้แต่ต้องมีคนรับไป** — เป็นเรื่องความปลอดภัยของระบบเดิม
> ไม่ใช่การตัดสินใจออกแบบของ SGI · บันทึกไว้ที่ `DECISIONS-รอตัดสินใจ.md` ข้อ **4.6** (กลุ่ม "ต้องไปถาม/ตาม")
