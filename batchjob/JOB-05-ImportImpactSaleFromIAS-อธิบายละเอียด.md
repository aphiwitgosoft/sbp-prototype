## 2. ทำไมต้องมี job นี้

ระบบจะจ่ายชดเชยก็ต่อเมื่อพิสูจน์ได้ว่า **ยอดขายตกจริงเพราะร้านใหม่เปิด** ไม่ใช่ตกตามฤดูกาลหรือภาวะตลาด

วิธีพิสูจน์คือ **เทียบสองชั้น**:

1. **ชั้นแรก** — เทียบ *ก่อนเปิด* กับ *หลังเปิด* ของปีนี้
2. **ชั้นที่สอง** — เทียบผลนั้นกับ *ช่วงเดียวกันของปีที่แล้ว* เพื่อหักผลตามฤดูกาลออก

ถ้าอัตราเติบโตหลังเปิด **แย่ลงกว่า**ก่อนเปิด (เทียบปีต่อปีแล้ว) แปลว่าร้านใหม่กระทบจริง

**สายข้อมูลเต็ม:** `Job 4` (ขอยอดขาย) → IAS/MIS → **`Job 5` (รับ + คำนวณ + ตัดสิน Y/N)** → `Job 8b` (เปิด workflow เฉพาะที่เป็น `Y`)

## 3. ภาพรวมการทำงาน

```
① หาไฟล์ AMS06001I_* ในโฟลเดอร์ขาเข้า
     │ ไม่มีไฟล์ ──▶ จบ (ถือว่าสำเร็จ) พร้อมโน้ต IF02001
     ▼
② อ่านไฟล์ทีละบรรทัด → จัดกลุ่มตาม (ร้าน + วันเปิดร้านใหม่)
     │   นับ "จำนวนวันทำการ" ต่อกลุ่ม
     │   คำนวณว่าแต่ละบรรทัดอยู่ในหน้าต่างไหน (1 ใน 4)
     ▼
③ transaction เดียว 7 คำสั่ง:
     insert ยอดขายรายวัน → update วันทำการ → ตัดสิน "ไม่ต้องคำนวณ" (Y)
     → update ยอดขายซ้ำ → คำนวณ growth rate → ตัดสิน Y/N → บันทึกการรับไฟล์
     ▼
④ backup ไฟล์ + ส่งเมล
     ▼
⑤ ลบไฟล์ขาออกที่เก่ากว่า 1 เดือน (เก็บกวาดของ Job 4)
```

### 🔴 เรื่องที่ต้องรู้ก่อนอย่างอื่น — 4 หน้าต่างเวลา

ทุกอย่างในการคำนวณอ้างอิงจาก **วันเปิดร้านใหม่ (`OPENDATE_N`)** เท่านั้น

```
        ปีที่แล้ว                              ปีนี้
   ┌─────────────┬─────────────┐        ┌─────────────┬─────────────┐
   │  หน้าต่าง 1  │  หน้าต่าง 2  │        │  หน้าต่าง 3  │  หน้าต่าง 4  │
   │ before PAST │ after PAST  │        │before PRESENT│after PRESENT│
   │  −15 ถึง −1 │  +1 ถึง +15 │        │  −15 ถึง −1 │  +1 ถึง +15 │
   └─────────────┴─────────────┘        └─────────────┴─────────────┘
          ▲ OPENDATE_N − 1 ปี                    ▲ OPENDATE_N
```

| # | ชื่อในโค้ด | ช่วง | ใช้ทำอะไร |
|---|---|---|---|
| 1 | `BEFORE_IMPACT_PAST` | (วันเปิด − 1 ปี) − 15 ถึง −1 วัน | ฐานเทียบ "ก่อน" ของปีที่แล้ว |
| 2 | `AFTER_IMPACT_PAST` | (วันเปิด − 1 ปี) + 1 ถึง +15 วัน | ฐานเทียบ "หลัง" ของปีที่แล้ว |
| 3 | `BEFORE_IMPACT_PRESENT` | วันเปิด − 15 ถึง −1 วัน | "ก่อน" ของปีนี้ |
| 4 | `AFTER_IMPACT_PRESENT` | วันเปิด + 1 ถึง +15 วัน | "หลัง" ของปีนี้ |

> 📌 **วันเปิดร้านใหม่เองไม่ถูกนับ** — ทั้งสี่หน้าต่างเว้นวันนั้นไว้ (`−1` และ `+1`)
> รวม **60 วัน** ซึ่งตรงกับค่าคงที่ `TOTAL_INTERVAL_DAY = 60` ที่ใช้ตรวจว่าข้อมูลครบ

### กติกาพิเศษ 29 กุมภาพันธ์

```java
if (cal.getActualMaximum(Calendar.DATE) > 28 && cal.get(Calendar.MONTH) == 1
        && cal.get(Calendar.DATE) == 28) {
    cal.add(Calendar.DATE, 1);   // use 29 FEB
}
```

ถ้าย้อนหลัง 1 ปีแล้วตกวันที่ **28 ก.พ. ของปีอธิกสุรทิน** ให้เลื่อนเป็น **29 ก.พ.**

**ทำไมต้องมี** — ร้านเปิด 28 ก.พ. 2026 (ปีปกติ) ย้อนไป 1 ปีได้ 28 ก.พ. 2025
แต่ถ้าร้านเปิด 1 มี.ค. 2025 ย้อนไปได้ 1 มี.ค. 2024 ซึ่ง**ข้าม 29 ก.พ. 2024 ไป**
โค้ดนี้พยายามให้หน้าต่างของสองปีมีจำนวนวันเท่ากัน

> 🔴 **แต่โค้ดนี้ทำงานเฉพาะกรณีเดียว** — เช็คว่า *ผลลัพธ์หลังย้อนปี* เป็น 28 ก.พ. ในปีอธิกสุรทิน
> ไม่ได้จัดการกรณี **ร้านเปิด 29 ก.พ.** (ย้อนไป 1 ปีจะได้ 28 ก.พ. ปีปกติ — Java ปัดให้เอง)
> **ต้องตัดสินว่าระบบใหม่ใช้กติกาเดียวกันหรือไม่** (ดูหัวข้อ 11)

```
\A ams06001i_ (\d{4}) ((0[1-9])|(1[0-2])) (([0][1-9])|([1-2][0-9])|(3[0-1])) (([0-1][0-9])|(2[0-3])) ([0-5][0-9]) \.txt $
```

> แต่ในทางปฏิบัติไม่กระทบเพราะชื่อไฟล์ไม่ได้ถูกใช้คำนวณอะไร

## 5. ขั้นที่ ② — อ่านไฟล์และจัดกลุ่ม

### รูปแบบไฟล์ — 4 ฟิลด์ต่อบรรทัด

```
00044|20260315|20260228|15234.50
  │      │        │        └── ยอดขายของวันนั้น
  │      │        └─────────── วันที่ขาย (วันทำการ)
  │      └──────────────────── วันเปิดร้านใหม่ (คีย์จับคู่กับที่ Job 4 ส่งไป)
  └─────────────────────────── รหัสร้าน SP
```

| ฟิลด์ | ดัชนีในโค้ด | ความหมาย |
|---|---|---|
| 1 | `[0]` | `STORECODE_I` |
| 2 | `[1]` | `OPENDATE_N` (`yyyyMMdd`) |
| 3 | `[2]` | วันที่ขาย |
| 4 | `[3]` | ยอดขาย |

> ⚠️ **encoding เป็น WINDOWS-874** ตามสัญญาไฟล์เดิม (ต่างจากไฟล์ขาออกของ Job 4 ที่เป็น UTF-8)

### 🔴 `MONTH`/`YEAR` มาจาก "วันเปิดร้านใหม่" ไม่ใช่งวดที่ขอ

```java
cal.setTime(impactStore.getOpenDateN());
impactStore.setYear(cal.get(Calendar.YEAR));
impactStore.setMonth(cal.get(Calendar.MONTH) + 1);
```

**นี่คือจุดที่เข้าใจผิดกันบ่อยที่สุด** — งวด (`MONTH`/`YEAR`) ที่ใช้ผูกกลับไปหาหัวสรุปยอดขาย
**ไม่ใช่งวดที่ Job 2 นำเข้า** แต่เป็น **เดือน/ปีของวันที่ร้านใหม่เปิด**

> 📌 ต้องตรงกับที่ Job 4 เขียนลงหัวสรุป — Job 4 ก็ copy `MONTH`/`YEAR` มาจากคู่ร้านของ Job 2
> **ถ้าสองฝั่งนิยามงวดไม่ตรงกัน แถวจะจับคู่ไม่เจอแล้วยอดขายจะลอย** (ดูหัวข้อ 11)

### การจัดกลุ่มและนับวันทำการ

โค้ดวนอ่านทีละบรรทัด แล้ว **ตรวจว่าเปลี่ยนกลุ่มหรือยัง** โดยเทียบ `storeCodeI` และ `openDateN` กับแถวก่อนหน้า

```java
if (i != 0 && (!equalsIgnoreCase(storeCodeI, storeCodeITemp) || !openDateN.equals(openDateNTemp))) {
    // ปิดกลุ่มเดิม: บันทึก countWorkingDays แล้วเริ่มนับใหม่
}
countWorkingDays++;
```

🔴 **วิธีนี้ตั้งอยู่บนสมมติฐานว่าไฟล์ถูกเรียงมาแล้ว** — ถ้า IAS ส่งแถวของร้านเดียวกันแบบสลับกัน
**จะนับวันทำการเป็นหลายกลุ่มย่อยและได้ตัวเลขผิด** โดยไม่มีอะไรเตือน

> ⚠️ Job 4 เรียงไฟล์ขาออกด้วย `ORDER BY OPENDATE_N, STORECODE_I` แต่ **ไม่มีอะไรรับประกันว่า IAS จะเรียงขากลับให้**
> **ระบบใหม่ต้องจัดกลุ่มด้วยโครงสร้างข้อมูล (Map) ไม่ใช่พึ่งลำดับในไฟล์**

### 🔴 `countWorkingDays` นับรวมแถวที่ถูกข้ามด้วย

```java
countWorkingDays++;
if (importService.countImpactStoreSalesTrn(storeCodeI, year, month) > 0) {
    continue;    // ข้ามแถวนี้ ไม่ insert
}
```

`countWorkingDays++` อยู่ **ก่อน** `continue` → แถวที่ถูกข้ามเพราะนำเข้าไปแล้ว **ยังถูกนับเป็นวันทำการ**

**ผลคือ** ถ้ารันซ้ำไฟล์เดิม ยอด `TOTAL_WORKING_DAY` ยังเท่าเดิม (ถูกโดยบังเอิญ ✅)
แต่ถ้าไฟล์มีแถวปนของงวดที่นำเข้าแล้วกับงวดใหม่ **ตัวเลขจะเพี้ยน**

### ⚠️ query กันซ้ำยิงทีละแถว

`countImpactStoreSalesTrn(...)` ถูกเรียก **ทุกบรรทัดของไฟล์** — ไฟล์ 60 วัน × 500 ร้าน = 30,000 query

> ✅ **ระบบใหม่ต้องอ่านชุดที่นำเข้าแล้วมาครั้งเดียว** แล้วเทียบในหน่วยความจำ

### `selectSeq` — ตัวจับคู่วันในหน้าต่าง

```java
public int selectSeq(Date impactSale, Date saleDate)   // คืนค่าห่างเป็นวัน
```

ใช้จับคู่ยอดขาย **วันที่ N ของหน้าต่างปีนี้** กับ **วันที่ N ของหน้าต่างปีที่แล้ว**
เพื่อให้เทียบกันแบบ "วันต่อวัน" ไม่ใช่แค่ค่าเฉลี่ยรวม

> ⚠️ **โค้ดวน `lstImpactStore` เพื่อหาแถวที่ `seq` ตรงกันแล้ว `remove(j)`** — เป็น O(n²) และ
> **แก้ไข list ระหว่างวน** ซึ่งเปราะมาก · ระบบใหม่ควรใช้ Map คีย์ด้วย `(ร้าน, วันเปิด, seq)`

## 6. ขั้นที่ ③ — 7 คำสั่งใน transaction เดียว

`ImportService.manageImpactSale()` รัน 7 อย่างเรียงกัน:

### ขั้นที่ 3 — กฎ "pre-accept" (ผ่านโดยไม่ต้องคำนวณ)

```sql
UPDATE FGI_IMPACT_STORE_SALES
   SET FLAG_VERIFY = 'Y', UPDATE_DATE = SYSDATE
 WHERE FLAG_VERIFY IN ('W','P')
   AND ( OPENDATE_I > TRUNC(ADD_MONTHS(OPENDATE_N, -12) - 15)   -- ร้านเก่าอายุไม่ถึง
      OR TOTAL_WORKING_DAY != 60 )                              -- ข้อมูลไม่ครบ 60 วัน
```

| เงื่อนไข | ความหมาย | ผล |
|---|---|---|
| **A1** ร้านเก่าเปิดหลัง (วันเปิดร้านใหม่ − 12 เดือน 15 วัน) | ร้านเก่ายังใหม่เกินไป — **ไม่มีข้อมูลปีที่แล้วให้เทียบ** | **`Y`** |
| **A2** `TOTAL_WORKING_DAY ≠ 60` | ข้อมูลยอดขายไม่ครบทั้ง 4 หน้าต่าง | **`Y`** |

> 🔴 **ตรรกะกลับด้านจากที่หลายคนคาด** — "ข้อมูลไม่ครบ" ทำให้ร้าน **ผ่าน** ไม่ใช่ตกไป
> เพราะระบบไม่สามารถพิสูจน์ได้ว่า *ไม่* กระทบ จึงให้ประโยชน์แก่ร้านแล้วส่งให้คนพิจารณาต่อ
> **นี่คือกติกาธุรกิจ ไม่ใช่บั๊ก** — ตรงกับที่ผังระบุว่า "อายุร้าน < 12ด.15ว. หรือวันทำการ < 60 → Y"

> ⚠️ **แต่ `!= 60` ครอบคลุมทั้งน้อยกว่าและมากกว่า** — ถ้า IAS ส่งมา 61 วันก็ได้ `Y` เหมือนกัน
> ต้องยืนยันว่าตั้งใจ หรือควรเป็น `< 60`

> ⚠️ **A1 ซ้ำกับกติกา T1 ของ Job 4** — Job 4 คัดร้านที่ไม่ผ่าน T1 ออกไปแล้วตั้งแต่ต้น
> ร้านที่มาถึง Job 5 จึงควรผ่าน A1 อยู่แล้วเสมอ · **เป็นตาข่ายกันพลาดชั้นสอง** (defensive)

### ขั้นที่ 5 — สูตรคำนวณ growth rate

```
growth_rate_before = (AVG_BEFORE_PRESENT − AVG_BEFORE_PAST) / AVG_BEFORE_PAST × 100
growth_rate_after  = (AVG_AFTER_PRESENT  − AVG_AFTER_PAST ) / AVG_AFTER_PAST  × 100
growth_rate_diff   = growth_rate_after − growth_rate_before
```

**อ่านเป็นภาษาคน**

| ค่า | ความหมาย |
|---|---|
| `growth_rate_before` | ก่อนร้านใหม่เปิด ร้านนี้โตขึ้นกี่ % เทียบปีที่แล้ว |
| `growth_rate_after` | หลังร้านใหม่เปิด ร้านนี้โตขึ้นกี่ % เทียบปีที่แล้ว |
| **`growth_rate_diff`** | **ความต่างของสองค่านั้น** — ติดลบ = หลังเปิดแย่ลงกว่าก่อนเปิด |

### 🔴 `DECODE(ตัวหาร, 0, NULL, ตัวหาร)` — ตัวหารเป็นศูนย์ให้ผลเป็น NULL

```sql
(AVG_BEFORE_IMPACT_PRESENT - DECODE(AVG_BEFORE_IMPACT_PAST, 0, NULL, AVG_BEFORE_IMPACT_PAST))
  / DECODE(AVG_BEFORE_IMPACT_PAST, 0, NULL, AVG_BEFORE_IMPACT_PAST) * 100
```

ถ้าปีที่แล้วยอดขายเฉลี่ยเป็น **0** (ร้านปิด · ไม่มีข้อมูล) → **หลีกเลี่ยงการหารด้วยศูนย์โดยให้ผลเป็น `NULL`**
`NULL` แพร่ต่อไปยัง `growth_rate_diff` ด้วย → **และนี่คือที่มาของความเสี่ยงในขั้นถัดไป**

### ตัวกรองยอดขายที่จับคู่ไม่ได้

ในการหา `AVG` มีเงื่อนไขซ้อนอยู่:

```sql
AVG( CASE WHEN DECODE(CHK_BEFORE_PAST,0,0,1) = DECODE(CHK_BEFORE_PRESENT,0,0,1) THEN SALES_BEFORE_PAST
          ELSE CASE WHEN CHK_DIFF_BEFORE_PAST = CHK_DIFF_BEFORE_PRESENT THEN SALES_BEFORE_PAST
                    ELSE 0 END
     END )
```

> 🔴 **แก้ 2026-09-13 — คำอธิบายเดิมในเอกสารนี้ตีความผิด 2 จุด** (เดิมเขียนว่าเงื่อนไขนี้
> เช็ค "มีข้อมูลครบทั้งสองฝั่งไหม" และ "นับเป็น 0 เพื่อไม่ให้ค่าเฉลี่ยเอียง")
> อ่านนิยามของ `CHK_*` ที่อยู่ท้ายคำสั่งเดียวกันแล้วพบว่าไม่ใช่ทั้งคู่

**นิยามจริงของตัวแปรในเงื่อนไข** (`ImportJdbc.java:544` และถัดลงไป):

```sql
-- ค่าเบี่ยงเบนรายวัน เป็น "เปอร์เซ็นต์" ไม่ใช่บาท
DIFF_BEFORE_IMPACT_PAST =
  ROUND( ((SALES - AVG(SALES) OVER (PARTITION BY STORECODE_I, MONTH, YEAR)) / SALES) * 100 )

CHK_DIFF_BEFORE_IMPACT_PAST = CASE WHEN ABS(DIFF_BEFORE_IMPACT_PAST) >= 50 THEN 1 ELSE 0 END  -- ธง outlier รายวัน
CHK_BEFORE_IMPACT_PAST      = SUM(CHK_DIFF_BEFORE_IMPACT_PAST) OVER (PARTITION BY ...)        -- จำนวน outlier ในหน้าต่าง
```

**แปลว่าจริง ๆ** — เงื่อนไขนี้ไม่เกี่ยวกับ "ข้อมูลขาด" เลย แต่เป็นเรื่อง **ค่าผิดปกติ (outlier)**:

1. ถ้าหน้าต่างปีก่อนกับปีนี้ **มี outlier เหมือนกัน** (มีทั้งคู่ หรือไม่มีทั้งคู่) → เฉลี่ยยอดขายทุกวันตามปกติ
2. ถ้า **มี outlier ข้างเดียว** → ไล่ดูรายวัน: นับยอดจริงเฉพาะวันที่ธง outlier ของปีก่อน = ของปีนี้
   วันที่ธงไม่ตรงกันจะถูก **แทนด้วย 0**

> 🔴 `ELSE 0` **ไม่ใช่การตัดวันนั้นทิ้ง** — ตัวหารของ `AVG` ยังเป็น 15 เท่าเดิม
> ค่าเฉลี่ยจึงถูก**กดลงทั้งสองฝั่งพร้อมกัน** (สูตรสมมาตร ปีก่อนกับปีนี้โดนวันเดียวกัน)
> ถ้าเผลอเขียนเป็น `WHERE ...` แล้วตัดแถวทิ้ง ผลลัพธ์จะต่างทันที — และแปลว่าจ่ายเงินผิด

> ⚠️ ผลข้างเคียงของการ **หารด้วยยอดขายของวันนั้นเอง** (ไม่ใช่หารด้วยค่าเฉลี่ย):
> วันที่ยอด**ตก**ผิดปกติได้ค่า diff ติดลบมหาศาล (เข้าใกล้ −∞) ส่วนวันที่ยอด**พุ่ง**ได้ค่าจำกัดที่ +100
> เกณฑ์ 50 จึงจับ "วันยอดตก" ไวกว่า "วันยอดพุ่ง" อย่างมาก — เป็นพฤติกรรมของระบบเดิมที่ต้องคงไว้

> 📌 กลไก "จับคู่วันต่อวัน" ใช้ **`SEQ`** เป็นกุญแจ · ตารางเดิมเป็น**ตารางกว้าง** (1 แถว = 1 SEQ
> มี 4 ชุดยอดขายอยู่ในแถวเดียว) จึงจับคู่ได้ฟรี · ตารางใหม่ `sgi_sales_transactions` เป็น**ตารางแคบ**
> (1 แถว = 1 วัน) จึง **เพิ่มคอลัมน์ `seq` เข้าไปแล้วเมื่อ 2026-09-13** — ไม่มีคอลัมน์นี้ join คู่ปีไม่ได้เลย

### ขั้นที่ 6 — ตัดสิน Y/N

```sql
UPDATE FGI_IMPACT_STORE_SALES FISS
   SET FLAG_VERIFY = CASE WHEN NVL(GROWTH_RATE_DIFF, 0-1) < 0 THEN 'Y' ELSE 'N' END,
       UPDATE_DATE = SYSDATE
```

|---|---|

| ศูนย์หรือบวก | **`N`** — ไม่เข้าเกณฑ์ |

> 🔴 **นี่คือความเสี่ยงข้อใหญ่ที่สุดของ job นี้** — `NULL` แปลว่า **"คำนวณไม่ได้"**
> (ตัวหารเป็นศูนย์ · ข้อมูลปีที่แล้วไม่มี) แต่ระบบตีความเป็น **"เข้าเกณฑ์ชดเชย"** อัตโนมัติ
> ร้านที่ไม่มีข้อมูลเปรียบเทียบเลยจะได้ `Y` **โดยไม่มีธงบอกว่าตัวเลขนี้เชื่อไม่ได้**
>
> ⚠️ **แต่ `Y` ไม่ได้แปลว่าเข้า workflow** — Gate ของ Job 8b ใช้ `growth_rate_diff <= -10`
> ซึ่ง `NULL <= -10` ให้ผลเป็น `NULL` **ไม่ใช่ TRUE** → แถวนั้นจึง **ค้างที่ `workflow_generation_status = 'W'` ตลอดไป**
> (ดูหัวข้อ 6 · ตารางเทียบเกณฑ์)
>
> **ระบบใหม่ต้องแยกให้ออก** ระหว่าง "คำนวณแล้วติดลบ" กับ "คำนวณไม่ได้"
> ทางเลือกอยู่ในหัวข้อ 11

### 🔴 `sales_status = 'Y'` **ไม่ได้แปลว่าเข้า workflow**

นี่คือจุดที่เข้าใจผิดกันบ่อยที่สุดระหว่าง Job 5 กับ Job 8b — **สองที่ใช้เกณฑ์คนละตัวบนตัวเลขเดียวกัน**

| | เกณฑ์ | ที่มาในโค้ด |
|---|---|---|
| **Job 5** ตั้ง `sales_status` | `NVL(growth_rate_diff, -1) < 0` → `Y` | `ImportJdbc.updateStatusImpactStoreSaleByDiff` |
| **Job 8b** Gen Flow Gate | `growth_rate_diff <= -10` | `StartFlowJdbc.selectImpactStore` |

**ผลของแต่ละช่วงค่า**

| `growth_rate_diff` | Job 5 | Job 8b | ปลายทางจริง |
|---|---|---|---|
| `-15` | `Y` | ✅ ผ่าน | **เปิด workflow** |
| `-10` พอดี | `Y` | ✅ ผ่าน (`<=`) | เปิด workflow |
| **`-5`** (อยู่ระหว่าง −10 กับ 0) | **`Y`** | ❌ ไม่ผ่าน | 🔴 **ค้าง `workflow_generation_status = 'W'` ตลอดไป** |
| `0` | `N` | ❌ | จบ |
| `+3` | `N` | ❌ | จบ |
| **`NULL`** | **`Y`** (จาก `NVL(..., -1)`) | ❌ (`NULL <= -10` = `NULL`) | 🔴 **ค้าง `W` ตลอดไป** |

> 🔴 **แถวที่ `-10 < diff < 0` และแถวที่ `diff` เป็น `NULL` ไม่มีอะไรมาทำให้จบ**

>
> **เป็นปัญหาชนิดเดียวกับ "แถวตกร่อง" ของ Job 2** และบันทึกไว้ที่ `DECISIONS` ข้อ **2.32**

### `sgi_sales_transactions`

```sql
CREATE TABLE sgi_sales_transactions (
    id BIGSERIAL PRIMARY KEY,
    sales_summary_id BIGINT NOT NULL REFERENCES sgi_fgi_impact_sales_summaries(id) ON DELETE CASCADE,
    txn_date DATE NOT NULL, window_no SMALLINT NOT NULL CHECK (window_no BETWEEN 1 AND 4),
    sales_amount NUMERIC(14,2) NOT NULL, sales_diff NUMERIC(14,2),
    is_outlier BOOLEAN NOT NULL DEFAULT FALSE, source_checksum VARCHAR(64) NOT NULL,
    created_at TIMESTAMP NOT NULL DEFAULT CURRENT_TIMESTAMP,
    CONSTRAINT uq_sales_day_window UNIQUE (sales_summary_id, txn_date, window_no)
);
```

### 🔴 A — โครงเปลี่ยนจาก "แถวกว้าง" เป็น "แถวแคบ"

ระบบเดิมเก็บ **1 แถว = 1 วัน × 4 คอลัมน์คู่** (วันที่ + ยอดขาย ของทั้ง 4 หน้าต่าง)
ระบบใหม่เก็บ **1 แถว = 1 วัน × 1 หน้าต่าง** โดยมี `window_no` (1–4) บอกว่าอยู่หน้าต่างไหน

| | ระบบเดิม | ระบบใหม่ |
|---|---|---|
| จำนวนแถวต่อร้านต่องวด | ~15 แถว (คอลัมน์กว้าง) | **~60 แถว** (แถวแคบ) |
| ข้อดี | คำนวณ `AVG` ใน `SELECT` เดียวได้ง่าย | โครงสะอาด · query ต่อหน้าต่างได้ตรง ๆ |
| ข้อเสีย | คอลัมน์เยอะ · NULL เยอะ | **สูตร `AVG` ต้องเขียนใหม่ทั้งหมด** |

> 🔴 **สูตรคำนวณของระบบเดิมย้ายมาใช้ตรง ๆ ไม่ได้** — ต้องเขียนใหม่เป็น pivot ตาม `window_no`
> และ **ต้องพิสูจน์ว่าให้ผลเท่ากันกับของเดิม** ด้วยข้อมูลจริงก่อนขึ้นใช้งาน (ดูหัวข้อ 11)

### 🔴 B — คอลัมน์ที่เพิ่มใหม่ ยังไม่มีนิยาม

| คอลัมน์ | ระบบเดิม | สถานะ |
|---|---|---|
| `sales_diff` | ❌ ไม่มี | ผังระบุว่าเป็น "ผลต่างรายวัน" แต่**ไม่ได้บอกว่าลบกับอะไร** — ปีที่แล้ววันคู่กัน? |
| `is_outlier` | ❌ ไม่มี | เกณฑ์ `\|sales_diff\| ≥ 50` เป็น literal ในผัง · **50 หน่วยอะไร** (บาท? %?) |
| `source_checksum` | ❌ ไม่มี | **`NOT NULL`** — ต้องกำหนดว่าเป็น checksum ของไฟล์ทั้งไฟล์ หรือของแถว |
| `window_no` | ❌ ไม่มี (เป็นคอลัมน์แทน) | ต้อง map 4 หน้าต่างในหัวข้อ 3 ให้ตรงลำดับ **แล้วบันทึกว่าเลขไหนคือหน้าต่างไหน** |

> 🔴 **`source_checksum` เป็น `NOT NULL` โดยไม่มี `DEFAULT`** — insert ไม่ผ่านถ้าไม่ใส่ค่า

### 🔴 C — `total_working_days` เปลี่ยนความหมาย

| | ระบบเดิม | ระบบใหม่ |
|---|---|---|
| นับอะไร | จำนวนบรรทัดในไฟล์ต่อกลุ่ม (**รวมแถวที่ถูกข้าม**) | ผังระบุ "จำนวนแถวดิบทั้งหมด (raw count)" |
| ใช้ทำอะไร | เทียบกับ `60` เพื่อ pre-accept | เหมือนกัน |

**ต้องระบุให้ชัดว่านับ "แถวในไฟล์" หรือ "แถวที่ insert สำเร็จ"** — สองอย่างนี้ต่างกันเมื่อมีแถวถูกข้าม

### `sgi_interface_transactions` — ค่าที่ Job 5 ต้องใส่

## 9. ตัวเลขที่ job ต้องรายงานทุกรอบ

| ชื่อ | นับอะไร | ตรวจอะไรได้ |
|---|---|---|
| `fileCount` · `fileName` · `fileChecksum` | ไฟล์ที่ประมวลผล | ตามรอยกลับไปหาไฟล์ต้นทางได้ |
| `sourceLineCount` | บรรทัดในไฟล์ | เทียบกับที่ IAS แจ้ง |
| `skippedAlreadyImportedCount` | แถวที่ข้ามเพราะนำเข้าแล้ว | รันซ้ำควรเข้าช่องนี้เกือบทั้งหมด |
| `insertedCount` | แถวยอดขายที่ insert | `source − skipped = inserted` |
| `unmatchedStoreCount` | 🔴 แถวที่หา**หัวสรุปไม่เจอ** | **> 0 ต้อง alert** — IAS ส่งร้านที่เราไม่ได้ขอ หรืองวดไม่ตรงกัน |
| `preAcceptedCount` | ร้านที่ได้ `Y` จากกฎ A1/A2 | สัดส่วนสูงผิดปกติ = ข้อมูลจาก IAS ไม่ครบบ่อย |
| `calculatedCount` | ร้านที่คำนวณ growth rate จริง | |
| **`invalidLineCount`** | 🔴 **บรรทัดที่ข้อมูลเสีย** — บรรทัดว่าง · ฟิลด์ไม่ครบ 4 · ยอดขายไม่ใช่ตัวเลข · วันที่แปลงไม่ได้ | **> 0 ต้อง alert** — ข้อมูลจาก IAS ผิดรูป |
| `acceptedCount` (`Y`) · **`businessRejectedCount`** (`N`) | 🔴 **ผลการประเมินทางธุรกิจ** — ไม่ใช่ข้อมูลเสีย | สัดส่วนผิดปกติเทียบงวดก่อนไหม |
| **`nullDiffCount`** | 🔴 ร้านที่ `growth_rate_diff` เป็น **NULL** แล้วได้ `Y` | **> 0 ต้อง alert** — ตัวเลขเชื่อไม่ได้ **และจะค้างที่ Job 8b ตลอดไป** |
| `outlierCount` | แถวที่ `is_outlier = true` | ข้อมูลจาก IAS ผิดปกติไหม |
| `durationMs` | เวลาที่ใช้ | |

**สมการที่ต้องเป็นจริงเสมอ:**

```
sourceLineCount − invalidLineCount − skippedAlreadyImportedCount − unmatchedStoreCount  =  insertedCount
preAcceptedCount + acceptedCount + businessRejectedCount                               =  จำนวนหัวสรุปที่ถูกตัดสินในรอบนี้
```

> 🔴 **ต้องแยกสองคำนี้ให้ขาดจากกัน** — ระบบเดิมไม่มีตัวนับ "ข้อมูลเสีย" เลย
> **`invalidLineCount`** = บรรทัดที่อ่านไม่ได้ (ปัญหาทางเทคนิค · ต้องแก้ที่ต้นทาง)
> **`businessRejectedCount`** = ร้านที่ประเมินแล้วไม่เข้าเกณฑ์ (ผลทางธุรกิจ · ถูกต้องตามกติกา)
> ถ้ารวมกันเป็นตัวเดียว **จะแยกไม่ออกว่าไฟล์พังหรือร้านไม่เข้าเกณฑ์**

> 🔴 **ยังต้องเคาะว่า malformed row ทำให้ reject รายแถว หรือ fail ทั้งไฟล์** (ดูหัวข้อ 11)
> และทุกแถวที่ reject ต้องเก็บ **เหตุผล + เลขบรรทัดในไฟล์ต้นทาง** เพื่อ audit/retry

- 🔴 **alert เมื่อ `nullDiffCount > 0`** — ร้านที่คำนวณไม่ได้กำลังถูกส่งเข้า workflow
- 🔴 **alert เมื่อ `unmatchedStoreCount > 0`** — ยอดขายลอย ไม่มีเจ้าของ

## 11. สิ่งที่ต้องตัดสินใจก่อนเริ่มเขียนโค้ด

| เรื่อง | คำถาม | สถานะ |
|---|---|---|
| 🔴 **`growth_rate_diff` เป็น NULL แล้วได้ `Y`** | `NVL(GROWTH_RATE_DIFF, -1) < 0` แปลง "คำนวณไม่ได้" เป็น "เข้าเกณฑ์ชดเชย" · เลือก **(ก) คงพฤติกรรมเดิม** (ให้ประโยชน์แก่ร้าน) + **เพิ่มธงบอกว่าตัวเลขเชื่อไม่ได้** · **(ข) แยกเป็นสถานะที่สาม** (`E` มีในโดเมนอยู่แล้ว) ให้คนตรวจก่อน · **(ค) ให้เป็น `N`** | 🔴 **ต้องเคาะ + ขอ business sign-off** — กระทบว่าจะจ่ายเงินหรือไม่จ่าย · ทาง ข. ใช้ `sales_status = 'E'` ที่ DDL รองรับอยู่แล้ว |
| 🔴 **สูตร `AVG` ต้องเขียนใหม่ทั้งหมด** | โครงเปลี่ยนจากแถวกว้าง (4 คู่คอลัมน์) เป็นแถวแคบ (`window_no` 1–4) · สูตรเดิมย้ายมาตรง ๆ ไม่ได้ | 🔴 **ต้องพิสูจน์ด้วยข้อมูลจริง** ว่าสูตรใหม่ให้ผลเท่าเดิม ก่อนขึ้นใช้งาน — ผิดแปลว่าจ่ายเงินผิด |
| 🔴 **`sales_diff` · `is_outlier` · `source_checksum` ยังไม่มีนิยาม** | สามคอลัมน์นี้**ไม่มีในระบบเดิม** · `sales_diff` ลบกับอะไร · `\|sales_diff\| ≥ 50` เป็นหน่วยอะไร · `source_checksum` เป็น `NOT NULL` ไม่มี DEFAULT | 🔴 **ต้องเคาะก่อนเขียนโค้ด** — insert ไม่ผ่านถ้าไม่มีนิยามของ `source_checksum` |
| 🔴 **`window_no` 1–4 คือหน้าต่างไหน** | DDL มีแค่ `CHECK (window_no BETWEEN 1 AND 4)` ไม่ได้บอกว่าเลขไหนคือหน้าต่างไหน | 🔴 **ต้องบันทึกให้ชัด** — Job 8b และหน้าจอจะอ่านตารางนี้ต่อ |
| 🔴 **`!= 60` หรือ `< 60`** | ระบบเดิมใช้ `TOTAL_WORKING_DAY != 60` → ข้อมูล **มากกว่า** 60 วันก็ได้ `Y` ด้วย | 🔴 **ต้องยืนยัน** — ผังเขียนว่า "วันทำการ < 60 → Y" ซึ่ง**ไม่ตรงกับโค้ด** |
| 🔴 **นิยาม "งวด" ต้องตรงกับ Job 4** | Job 5 คำนวณ `MONTH`/`YEAR` จาก **วันเปิดร้านใหม่** ไม่ใช่งวดที่นำเข้า · ต้องตรงกับที่ Job 4 เขียนลงหัวสรุป | 🔴 **ต้องยืนยัน** — ถ้าไม่ตรง แถวจับคู่ไม่เจอแล้วยอดขายลอย (เคสทดสอบ 4.8) · ผูกกับข้อ **2.25** |
| **กติกา 29 กุมภาพันธ์** | โค้ดเดิมเลื่อน 28 ก.พ. เป็น 29 ก.พ. เฉพาะกรณีเดียว · ไม่ได้จัดการร้านที่เปิด 29 ก.พ. | ⏳ ต้องระบุกติกาให้ครบทุกกรณี |
| **การลบไฟล์ขาออกของ Job 4** | Job 5 ไปลบไฟล์ในโฟลเดอร์ของ Job 4 — หน้าที่ปนกันข้าม job | ⏳ **ย้ายไปเป็น S3 lifecycle policy** ไม่ใช่ให้ job ทำ |
| **ไฟล์ต้นทางไม่ถูกลบ** | เป็น copy ไม่ใช่ move — โฟลเดอร์ขาเข้าโตไม่มีที่สิ้นสุด | ⏳ ระบบใหม่บน S3 ใช้ lifecycle policy |

| **L2** | **จัดกลุ่มโดยพึ่งลำดับแถวในไฟล์** | `ImportController` — เทียบ `storeCodeITemp`/`openDateNTemp` กับแถวก่อนหน้า | จัดกลุ่มด้วย **Map** คีย์ `(ร้าน, วันเปิด)` — ไม่ขึ้นกับลำดับที่ IAS ส่งมา |
| **L3** | **นับวันทำการก่อนตรวจว่าจะข้ามแถวหรือไม่** | `countWorkingDays++` อยู่ก่อน `continue` | ระบุให้ชัดว่านับ "แถวในไฟล์" หรือ "แถวที่ insert" แล้วทำตามนั้น |
| **L4** | **query กันซ้ำยิงทีละแถว** | `countImpactStoreSalesTrn(...)` ถูกเรียกทุกบรรทัด — ไฟล์ 30,000 บรรทัด = 30,000 query | อ่านชุดที่นำเข้าแล้วมา**ครั้งเดียว** แล้วเทียบในหน่วยความจำ |
| **L5** | **วน list แล้ว `remove` ระหว่างวน** | หา `seq` ที่ตรงกันแล้ว `lstImpactStore.remove(j)` — O(n²) และเปราะ | ใช้ **Map** คีย์ `(ร้าน, วันเปิด, seq)` |
| **L6** | **transaction ซ้อนสองชั้น** | `ImportService.manageImpactSale` บรรทัด 104-124 — `TransactionTemplate.execute()` แล้วเขียนทับ `status` ด้วย `getTransaction()` ตัวใหม่ + `commit()` เอง | **transaction ชั้นเดียว** ปล่อยให้ framework จัดการ (เหมือน Job 2 · L5) |
| **L7** | **DAO กลืน exception แล้วคืน 0** | `updateStatusImpactStoreSalesByDays` · `calculateGrowthRate...` · `updateStatusImpactStoreSaleByDiff` — ทั้งสาม `catch` แล้ว `return result` (= 0) | ⚠️ **ร้ายแรงเป็นพิเศษ** — ถ้าขั้นคำนวณล้ม transaction จะ **commit ไปตามปกติ** โดยไม่มีใครรู้ว่าไม่ได้คำนวณ · ต้องโยน exception ให้ rollback |
| **L8** | **`Integer.parseInt(STORECODE_I)`** | ประกอบ `ConfirmReceiveData` — รหัสร้าน `00044` → `44` · รหัสที่มีตัวอักษรจะล้มทั้ง job | เก็บเป็น **ข้อความ** (`business_key VARCHAR`) — เหมือน Job 4 · L7 |
| **L9** | **ส่งเมลเฉพาะเมื่อมีข้อมูล** | `if (lstInsertImpactStore.size() > 0)` — ไฟล์ที่ทุกแถวถูกข้ามจะเงียบสนิท ไม่ backup ด้วย | รายงานทุกรอบ · แยก "ไม่มีไฟล์" · "ไฟล์ซ้ำ" · "ประมวลผลแล้ว" ให้ชัด |
| **L10** | **Job 5 ไปลบไฟล์ของ Job 4** | `queryDeleteFileImpactStoreSales1MonthAgo` แล้วลบใน `out/IAS/` | **S3 lifecycle policy** — job ไม่ควรเก็บกวาดพื้นที่ของ job อื่น |
| **L11** | **ไฟล์ต้นทางถูก copy ไม่ใช่ move** | `backupFile(file, backupFile)` ใช้ `copyFile` | ย้ายจริง หรือใช้ lifecycle policy · ไม่ปล่อยให้โฟลเดอร์โตไม่มีที่สิ้นสุด |

> ⚠️ **L1 + L7 รวมกันคือความเสี่ยงที่ร้ายที่สุดของ job นี้**
> ขั้นคำนวณล้มเงียบ → `growth_rate_diff` ไม่ถูกเขียน (คงเป็น NULL) → `NVL(..., -1)` ตีความเป็น **`Y`**
> → ร้านไหลเข้า workflow ให้คนอนุมัติจ่ายเงิน **ทั้งที่ระบบไม่เคยคำนวณอะไรเลย**
