1. สถาปัตยกรรมระบบใหม่ — แยก Frontend / Backend

BE / FE Split

จุดเปลี่ยนสำคัญ: ไม่มี BPM/K2 engine ภายนอกอีกต่อไป — การเปิดและเดิน workflow ใช้ @srm/glb-workflow ซึ่งเป็น engine ที่ระบบ SBP ปัจจุบันใช้งานจริงอยู่แล้ว (ตัดสินใจ 2026-08-06 · ไม่เขียน engine เอง) — Jobs 7/8/9 เขียนฐานข้อมูลตรงผ่าน Document Service และ Job 8b เปิด workflow ผ่าน POST /workflows/instances ส่วน interface กับระบบภายนอก (QSSI, ALLMAP, IAS, STA) ยังเป็นขอบเขตของทีมอื่น — QSSI/ALLMAP คงกลไกเดิม · IAS/MIS ย้ายไป EAI S3 · STA ย้ายไป RabbitMQ (มติ 2026-08-24)

ข้อเท็จจริงของ Workflow Engine จากฐานข้อมูลจริง (ยืนยัน 2026-08-10 · ที่มา SBP/db-schema-sps_store.md · SBP/db-schema-sps_auth.md · สรุปที่ SBP/SBPGI-vs-existing-system.md §3.1)
  • engine มี 13 ตาราง ไม่ใช่ 10 — workflow · workflow_version · workflow_state · workflow_status · workflow_event · workflow_route · workflow_group · workflow_group_map · workflow_transaction · workflow_history · workflow_approver · workflow_part · workflow_part_display
  • engine ตัวจริงอยู่ schema sps_store ไม่ใช่ sps_auth — สอง schema มีครบ 13 ตารางชื่อเดียวกันแต่คนละชุด/คนละเวอร์ชัน (workflow_state ของ sps_auth 3 คอลัมน์ / sps_store 4 คอลัมน์) · ปริมาณจริง sps_store: workflow_transaction 19,283 แถว · workflow_history 38,010 · workflow_approver 96,542 · ส่วน sps_auth เป็นชุดของ auth-backend (transaction 55 · route 41 · state 10)
  • ความเสี่ยงที่ต้องคุยกับทีมเจ้าของ library: sps_store.workflow_transaction ไม่มี PK และไม่มี index เลย ทั้งที่มี 19,283 แถว (ตัวเดียวกันใน sps_auth มี PK ปกติ) → seq-scan ทุก action · ยังไม่ตัดสินว่าจะขอ sign-off เพิ่ม index หรือกันซ้ำฝั่ง SBPGI — ดู DP-2
  • ✅ API ของ engine — ยึด LLDD ของ lib (ปิดข้อค้าง 2026-08-14): 8 function ตามชีต Detail ของ SBP/TSM-SRM-LLDD SBP workflow 1.2.xlsx — initializeWorkflow · eventWorkflow · getPermissionEvents · getHistory · getTransaction · getPendingFlowByUser · getWorkflowsByUser · addPreApprover · Trigger Event เป็นชื่อหัวข้อขั้นตอนภายใน eventWorkflow และ *UseCase เป็น wrapper ของ store-backend ไม่ใช่ API ของ lib
  • ✅ referenceId ปิดแล้ว 2026-08-17 — ใช้ compensation_documents.id (surrogate) ตามที่ระบบเดิม (cooperation-request · inform-evaluate) ทำจริงทุกจุด · ส่งเป็น string เพราะ sps_store.workflow_transaction.reference_id เป็น varchar(255) · ผลที่ตามมา: แก้ doc_no ภายหลังได้โดย workflow ไม่หลุด link · ⚠️ แต่ยังต้องออกเลขพร้อมตอน INSERT เสมอ — ตารางลูก 6 ตัว (document_new_stores · document_external_factors · document_competitors · document_cost_details · document_attachments · consideration_logs) FK ไป doc_no แบบ NOT NULL จึงบันทึกรายละเอียดเอกสารไม่ได้เลยถ้า doc_no ยังว่าง (Job 8 ออกเลขใน INSERT เดียวกันอยู่แล้ว)
  • workflow_part / workflow_part_display ของ engine คุม READ/WRITE รายส่วนของหน้าจอต่อ state ซึ่งทับซ้อนกับกลไก data-editrole/.edit-only ที่ prototype ทำเอง — เป็นข้อค้างตัดสินใจ ยังไม่เปลี่ยนดีไซน์

สัญญากลางที่ผูกกับ workflow: ดู LLDD-BE-API-Common-Contracts และ LLDD-FE-Integration-Contracts ก่อน implement ทุกจุดที่เรียก workflow API — POST /documents/{docNo}/actions รับ {result, comment} และคืน {nextSection, statusCode, status}; POST /workflows/instances ใช้ service token และ Gen Flow Gate W/Y/N อยู่ที่ BE Workflow Engine

4. พฤติกรรมจาก Approve Flow เดิมที่ยังต้องทำเพิ่ม

Flow ประกันรายได้.png

จากแผนภาพอนุมัติระบบเดิม (BPMN "A-Document Approve Flow ประกันรายได้") มี 4 พฤติกรรมที่ flow ด้านบนยังไม่ครอบคลุม — ทั้งหมดอยู่ฝั่งเอกสาร/Workflow (โซน B/C) ไม่กระทบ FGI/FCS pipeline (Jobs 1–10) และ interface ภายนอก

พฤติกรรมจาก flow เดิมระบบใหม่ขอบเขตผลกระทบ
อีเมลเตือนงานค้างรายสัปดาห์ ส่งอีเมลแจ้งเตือนผู้ดำเนินการ ทุกวันจันทร์ 10:00 แทบทุกขั้น (จุด 10.1, 20.2, 30.1, 70.1, 80.1, 110.2) email-lib กลาง (sendEmail) เพิ่ม reminder job รายสัปดาห์ อ่านงานค้างจาก sps_store.workflow_transaction/workflow_approver ของ @srm/glb-workflow (ตาราง workflow_tasks ถูกตัดไปแล้ว) · ผู้รับ = เจ้าของงานค้าง (business_user.email) · เมลกลุ่มนี้ไม่ใช่ transition จึงไม่มี route ให้แขวน email_id — เก็บเลข template ที่ mas_param แล้ว SBPGI เรียก sendEmail() เอง (ปิด DP-5 · 2026-08-14) · รอบเวลาแก้ได้ใน config โซน B/C · ไม่แตะ FGI/FCS
Escalation งานค้าง 30/45/60 วัน ส่งต่อไปยัง GM OPT เมื่องานค้างครบ 30, 45, 60 วัน (จุด 20.3) Workflow Engine ตรวจอายุงานค้าง (waitingDate จาก getPendingFlowByUser() ของ @srm/glb-workflow — ) แล้วแจ้ง/ส่งต่อหัวหน้า Section ตามเกณฑ์ 30/45/60 วัน (ค่ากำหนดแก้ได้) โซน B · ไม่แตะ FGI/FCS
สร้างเอกสารแบบ manual ขั้น 15 (lane admin): กรอกข้อมูลร้านเปิดใหม่/ร้านถูกกระทบเอง เมื่อระบบคำนวณให้ไม่ได้ สร้างข้อมูลต้นทางที่ระบบ FS → รอ SBP Statement ส่งกลับ (~1 วัน) → POST /documents ลงตารางชุดเดียวกับเส้นอัตโนมัติ · ไม่มีฟอร์มสร้างเอกสารใน FE (ตัดสินใจ 2026-08-06 — k2-create เหลือเป็นหน้าอธิบายกระบวนการ) โซน B · ไม่แตะ FGI/FCS
เงื่อนไขร้านก่อน/หลัง 1/10/2014 โน้ต 10.1–10.4 แยกจุดเริ่มเอกสารตามวันที่โอนร้านแฟรนไชส์ และกรณีไม่มีข้อมูลให้คำนวณ ถ้ายืนยันตาม SRS: ใช้เป็นกฎ routing ตอนเปิด instance ใน Workflow Engine — เกณฑ์ Gen Flow Gate ฝั่ง batch คงเดิมทุกข้อ · รอ verify กับ SRS v3.1 โซน B · ไม่แตะ FGI/FCS

กติกาธุรกิจทั้งหมดคงเดิมตามเอกสารอ้างอิง — เกณฑ์ Gen Flow Gate, กฎวงเงิน เกณฑ์เดียว 100,000 (SDD GI 24/02/2026), หน้าต่างคำนวณ 4×15 วัน, เกณฑ์ outlier ≥ 50, QSSI 6 หมวด, %ชดเชยรวม 100% ฯลฯ การเปลี่ยนแปลงจำกัดอยู่ที่กลไกทางเทคนิค (ไฟล์ภายใน → DB/API, K2 engine → Workflow ภายใน) และการแก้ความเสี่ยง P0/P1 ที่เอกสาร v4.0 ระบุ — การเปลี่ยนพฤติกรรมเชิงธุรกิจใด ๆ ต้องขออนุมัติแยกตามข้อ 8.2 ของเอกสาร
