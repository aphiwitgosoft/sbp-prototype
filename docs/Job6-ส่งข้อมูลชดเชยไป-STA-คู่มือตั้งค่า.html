1. job นี้ทำอะไร

ซิงก์สถานะรอบชดเชยประกันรายได้ในฐาน แล้วส่งผลไปให้ STA ผ่าน RabbitMQ (แทนไฟล์ FRBC0001_*.txt + SFTP ของระบบเดิม) — เป็น job ที่ทำให้เงินออกจริง ถ้าฐานกับสิ่งที่ STA ได้รับไม่ตรงกัน แปลว่าจ่ายซ้ำหรือไม่จ่าย
ชื่อ job sgi-export-impact-store-to-sta
โค้ดเดิม fgi.main.ExportImpactStoreToFS · ExportService.manageDBToFs · ExportJdbc
รอบการรัน ทุกวัน 0 17 * * * (UTC) = เที่ยงคืนเวลาไทย
ปลายทาง RabbitMQ exchange master.store → queue ของ STA

ลำดับการทำงาน

  1. อ่าน INPUT และแตกเป็นวันที่รัน · งวดซิงก์ · งวด QSSI
  2. ตรวจว่าตั้ง env ของ RabbitMQ ครบ 3 ตัว (ข้อ 3) — ไม่ครบ = ล้ม JOB6_MQ_CONFIG_MISSING ก่อนแตะฐาน (ยกเว้น dryRun)
  3. อ่านค่าคงที่จาก mas_param
  4. ตรวจ 2 ประตู - Gate 1 วันของเดือน ≥ SGI_STA_INIT_START_DAY (7) - Gate 2 คะแนน QSSI ของเดือนก่อนหน้ามีครบ 6 หมวด — ตรวจเฉพาะเมื่อผ่าน Gate 1 (วันที่ 1–6 ไม่อ่าน fcs_qssi_score) · คิวรีนี้ใช้ timeout ของตัวเอง SGI_JOB6_QSSI_TIMEOUT_MS
  5. ใน transaction เดียว — แก้ข้อมูล 9 ขั้น + บันทึกข้อความที่จะส่งลง sgi_interface_transactions (outbox สถานะ READY) - ข้อความของงวดเดือนที่รัน (สายเปิดรอบและสายผลอนุมัติ) - ผลอนุมัติของงวดก่อนหน้าที่ยังไม่เคยส่ง (ข้อ 7.1)
  6. หลัง commit — ส่งเข้า RabbitMQ รอ broker ยืนยันทีละข้อความ แล้วอัปเดต outbox · พร้อมส่งซ้ำข้อความที่ค้างจากรอบก่อน (backlog)
ขั้น ทำอะไร เงื่อนไข
① ปิดรอบที่ STA ตอบกลับครบแล้ว ทุกวัน
② รอบที่ส่งแล้วแต่ยังไม่ถึงกำหนดจ่าย Y → W ทุกวัน
③ เลื่อนงวดของรอบที่ชดเชยต่อเนื่อง ผ่านทั้ง 2 ประตู
④ เปิดรอบชดเชยใหม่ ผ่านทั้ง 2 ประตู
⑤ ⑥ สร้างแถวค่าชดเชยฝั่งร้านถูกกระทบ (I) และร้านเปิดใหม่ (N) ผ่านทั้ง 2 ประตู
⑦ ⑧ snapshot ข้อมูลร้านถูกกระทบ / ร้านเปิดใหม่ ณ งวดนั้น ผ่านทั้ง 2 ประตู
⑨ ตัดคู่ร้านที่ยอดขายไม่ตกออกจากกระบวนการ ผ่านทั้ง 2 ประตู

ไม่ผ่านประตู ไม่ได้หยุดทั้ง job — ขั้น ①② ทำทุกวัน และข้อความสายอนุมัติ (A N S Z) ยังถูกส่งตามปกติ QSSI จำเป็นเฉพาะตอนเปิดรอบใหม่

รอบที่ฝ่าย SBP DSA (06) ปิดเอกสารด้วย "เห็นควรไม่ชดเชย" หรือ "หยุดชดเชยประกันรายได้" ถูก BE ปิดรอบให้แล้ว (flag_action = N · process_status = CLOSED · งวดสิ้นสุด = งวดของเอกสาร) ขั้น ③④⑤ จึงไม่สร้างงวดใหม่ให้รอบนั้น แต่ผล N/S ของงวดนั้นยังถูกส่งไป STA ตามปกติ

สิ่งที่ต้องเตรียมฝั่ง broker (ทีม STA / ผู้ดูแล RabbitMQ)

  1. ผูก queue sta.sta.ss.frbc0001.queue เข้ากับ exchange master.store ด้วย routing key master.store.compensate-status job ไม่สร้างและไม่ผูก queue เอง (เหมือน job อื่นทุกตัวใน repo — ไม่มี assertQueue/bindQueue ในโค้ดเลย) ยังไม่ผูก = ข้อความถูกตีกลับ (mandatory) แถว outbox เป็น FAILED + UNROUTABLE แล้วส่งใหม่รอบถัดไป
  2. exchange master.store ต้องเป็นชนิด topic และ durable — job เรียก assertExchange('master.store', 'topic', { durable: true }) ทุกครั้ง ถ้ามีอยู่แล้วเป็นชนิดอื่น จะได้ PRECONDITION_FAILED และส่งไม่ออกทั้งชุด
  3. user ใน RABBITMQ_URL ต้องมีสิทธิ์ configure + write บน exchange นี้

5. สิ่งที่ต้องตั้งใน AWS

  1. Batch job definition ของ sgi-export-impact-store-to-sta - env ตามข้อ 3 - RABBITMQ_URL ดึงจาก Secrets Manager → execution role ต้องมี secretsmanager:GetSecretValue ของ secret นั้น - argv[3] = ชื่อ job · argv[2] = INPUT (JSON)
  2. Network — security group/subnet ของ compute environment ต้องต่อถึง broker (AMQPS 5671 · AMQP 5672) · ถ้าเป็น Amazon MQ ต้องเปิด inbound ฝั่ง broker ให้ SG ของ Batch
  3. EventBridge scheduled rule — cron(0 17 * * ? *) ทุกวัน · ส่ง INPUT ว่างหรือ {}
  4. Timeout ของ job — publisher ของ Job 6 ยังไม่มี timeout ตอนต่อ broker/รอ confirm ถ้า broker ค้าง job จะรอจนถึง timeout ของ AWS Batch จึงควรตั้ง attemptDurationSeconds ไว้
  5. ไม่ต้องเพิ่ม DB_STATEMENT_TIMEOUT ของ job definition เพื่อคิวรี QSSI อีกแล้ว — คิวรีนั้นใช้ SGI_JOB6_QSSI_TIMEOUT_MS ของตัวเอง

7.1 ผลอนุมัติของงวดก่อนหน้า (เพิ่ม 2026-10-14)

ผลอนุมัติออกตอนเอกสารจบ flow ซึ่งเดินหลายขั้น (06 → 08 → 06 → 01 → 02 → 03) จึงข้ามเดือนของงวดได้ เช่น งวด 2026-09 อนุมัติจบวันที่ 5 ต.ค. — เดิม Job 6 เลือกส่งเฉพาะงวดของเดือนที่รัน ผลของงวด 2026-09 จึงไม่เคยถูกส่ง

ตอนนี้ทุกรอบจะส่งเพิ่มเฉพาะงวดก่อนหน้าที่ครบทุกข้อ

เงื่อนไข ค่า
สถานะงวด A · N · S · Z
อยู่ในกรอบย้อนหลัง SGI_JOB6_APPROVE_LOOKBACK_MONTHS เดือน (ค่าตั้งต้น 3)
วันที่อนุมัติ ≥ SGI_JOB6_APPROVE_SINCE เมื่อตั้งไว้ (งวดที่ไม่มีวันอนุมัติ เช่น Z ใช้วันที่แก้ไขล่าสุดแทน)
ยังไม่เคยมีข้อความผลอนุมัติฝั่ง I ของงวดนั้น ไม่ว่าจะยืนยันแล้วหรือยังค้าง — ที่ค้างอยู่ backlog ส่งซ้ำให้เอง จึงไม่สร้างซ้ำ
  • ข้อความบันทึก outbox ด้วย period_key = งวดนั้นเอง (ไม่ใช่เดือนที่รัน) จึงไม่ชนกับข้อความของงวดปัจจุบันในรอบเดียวกัน
  • compensate_year_month ในข้อความเป็นงวดนั้น · คะแนน QSSI ใช้ของเดือนก่อนงวดนั้น เหมือนตอนส่งในเดือนของมันเอง
  • 🔴 ขึ้น production ต้องตั้ง SGI_JOB6_APPROVE_SINCE = วันเริ่มใช้ระบบ — ไม่ตั้ง = งวดที่ย้ายมาจากระบบเดิมในกรอบ 3 เดือนจะถูกส่งซ้ำ (ระบบเดิมส่งให้ STA ไปแล้ว)
  • วัดบน dev และ UAT วันที่ 2026-10-14: งวดที่เข้าเงื่อนไขย้อนหลัง 0 งวด — รันครั้งแรกไม่มีข้อความทะลัก
  • ⚠️ ข้อจำกัด: ข้อความผลอนุมัติของงวดหนึ่งที่ broker ยืนยันไปแล้ว ถ้าสถานะเปลี่ยนภายหลัง (เช่น ได้ Z จาก STA ก่อน แล้ว 06 ปิดด้วย N) สถานะใหม่จะไม่ถูกส่งซ้ำ — เป็นพฤติกรรมเดิมของ outbox

SELECT data_name, outbox_status, status, retry_count, return_message, count(*)
  FROM sps_store.sgi_interface_transactions
 WHERE direction = 'OUT'
 GROUP BY 1, 2, 3, 4, 5
 ORDER BY 1, 2;
outbox_status ความหมาย
READY บันทึกแล้ว ยังไม่เคยส่ง
CONFIRMED (+ status = COMPLETED) broker ยืนยันรับแล้ว
FAILED ส่งไม่สำเร็จ · รอบถัดไปส่งซ้ำ (จนกว่า retry_count จะถึงเพดาน)

ตรวจว่าผลอนุมัติของงวดใดถูกส่งแล้วหรือยัง

SELECT c.impacted_store_code, c.compensate_month, c.compensate_status, c.approve_date,
       t.outbox_status, t.status, t.created_at
  FROM sps_store.sgi_fgi_impact_compensations c
  JOIN sps_store.sgi_fgi_impact_processes p ON p.id = c.impact_process_id
  LEFT JOIN sps_store.sgi_interface_transactions t
         ON t.direction = 'OUT' AND t.data_name = 'COMPENSATE_APPROVE_I'
        AND t.business_key = c.impacted_store_code || '|' || p.impact_month
        AND t.period_key = c.compensate_month
 WHERE c.compensate_status IN ('A', 'N', 'S', 'Z')
 ORDER BY c.approve_date DESC NULLS LAST
 LIMIT 50;

9. ลำดับทดสอบบน UAT

  1. deploy store-backend รุ่นที่เขียน A/N/S และปิดรอบชดเชยตอนจบ flow (ไม่งั้นสายผลอนุมัติไม่มีอะไรให้ส่ง) และมีเส้นรับยอดจาก STA (POST /sgi/interface/sta-update-compensate รุ่นสัญญา 2026-10-27)
  2. ยืนยันข้อ 2 กับทีม STA (binding · ชนิด exchange · สิทธิ์ user)
  3. ตั้ง env + secret + network ตามข้อ 3 และ 5 (บน UAT ไม่ต้องตั้ง SGI_JOB6_APPROVE_SINCE)
  4. รัน INPUT={"dryRun":true} — ตรวจว่าผ่านด่าน QSSI และนับจำนวนที่จะส่งได้ (ไม่เขียนฐาน ไม่ส่ง MQ)
  5. รันจริง แล้วดู log + คิวรีในข้อ 8
  6. ให้ทีม STA ยืนยันว่ามีข้อความเข้า sta.sta.ss.frbc0001.queue และอ่านได้ครบ 14 ฟิลด์
  7. ทดสอบขาไปกลับครบวง: STA เรียก API ตรงส่งยอดกลับ → ผ่าน flow เอกสารจนอนุมัติ → รอบถัดไปของ Job 6 ส่งผล A ไป STA
