### 🔴 ข้อ 10 ตอบคำถามที่ค้างอยู่ใน `DECISIONS` ข้อ 2.36(1)

ข้อ 2.36(1) ตั้งข้อสังเกตว่าเกณฑ์เตือนงานค้างเป็น **ช่วงปิด** (`30-36` · `45-51` · `60-66`)
แล้วสรุปว่า *"เอกสารที่ค้าง 67 วันขึ้นไปไม่ถูกเตือนอีกเลยตลอดกาล ทั้งที่นั่นคือกรณีที่ควรดังที่สุด"*

**ของเดิมไม่ได้ปล่อยค้าง — พอครบ 67 วันระบบ *ยกเลิกเอกสาร* ทิ้งเลย**
หมายเหตุใน master เขียนไว้ตรงตัว และมีผลการพิจารณาคู่กันคือ `DecisionCode 14 ยกเลิกโดยระบบ`
(`CancelBySystem` · หมายเหตุ *"ยกเลิกเนื่องจากรองานเกินระยะเวลาที่กำหนด"*)

→ ช่วงเตือน `60-66` จึงเป็น **การเตือนครั้งสุดท้ายก่อนเอกสารถูกยกเลิก** ไม่ใช่ช่องโหว่
→ **แต่โครงใหม่ไม่มีทั้งสถานะ "ยกเลิกเอกสาร" และผลพิจารณา "ยกเลิกโดยระบบ"** — ต้องตัดสินว่าจะยกกติกา 67 วันมาด้วยไหม

### ⚠️ แถวขยะในฐาน production

`SectionCode = 10` ชื่อ `oo` หมายเหตุ `ooooooooo` — เป็นข้อมูลทดสอบที่ค้างอยู่ในตาราง master จริง

ผลวัดจากฐาน dev จริง (`output/legacy-sgi/data.json` · `zone_join`):

```
mas_store.zone_cd          = 10, 21, 70, 84, 85        ← เลข  = ZoneCode
business_user.zone_code    = BE, BN, BS, BW, RC, REU, RN, RS   ← ตัวอักษร = ZoneName
business_user.zone_cd      = 72, 73, 75, 76            ← เลขคนละชุด
overlap ของ zone_cd ทั้งสองฝั่ง = 0 ค่า
```

`ZoneProfile` แปลงเลข ↔ ตัวอักษรได้ตรง: `10`→`BN` · `70`→`BS` · `84`→`RSL` · `85`→`RN`
→ **สมมติฐาน:** เส้นทาง join ที่ถูกคือ
`mas_store.zone_cd` → `ZoneProfile.ZoneCode` → `ZoneName` = `business_user.zone_code`
ไม่ใช่ `business_user.zone_cd = mas_store.zone_cd` อย่างที่โค้ดเดิมเขียน

**ยังไม่ปิดเป็นข้อสรุป** เพราะ:
- `mas_store.zone_cd` มีค่า `21` ซึ่ง **ไม่มีใน `ZoneProfile`** (มีแต่ `20` = BW)
- `business_user.zone_code` มีค่า `RS` ซึ่ง **ไม่มีใน `ZoneProfile`** (มีแต่ `RSU`/`RSL`)
- บนฐาน dev ข้อมูลว่างเกือบหมดอยู่แล้ว (`mas_store.zone_cd` ว่าง 19,641/19,647 · `business_user` ว่างทั้งคู่ 12,745/12,759)
  → **ต่อให้ join ถูก ก็ยังหาผู้รับอีเมลไม่ได้อยู่ดีบน dev** ต้องทดสอบกับข้อมูล uat/prod
