SGI รับยอดเงินชดเชยประกันรายได้จาก STA

สัญญา API รับยอดชดเชย — STA เรียก HTTP ตรง เข้า store-backend ของ SGI

🔴 สัญญาใหม่ 2026-10-27 (มติผู้ใช้) — เส้นนี้ไม่ใช้ RabbitMQ แล้ว

  • ผู้เรียกคือ STA ยิง HTTP ตรงพร้อม header x-api-key · ไม่ผ่าน EAI consumer sta_cal_sgi และไม่ผ่าน BFF
  • คำขอ 1 ครั้ง = รายการเดียว (ร้านถูกกระทบ 1 ร้าน × 1 งวด) · ไม่มีซอง dataType/dataName/dataMessage/sender/sentAt แล้ว
  • คำตอบเป็นรูปของ web service ระบบเดิม {result, data, errorCode, errorMsg} (แทน {success, data:{status, results[]}})
  • รับ body รูปเดิมของ web service {"input":"<base64 ของ JSON รายการ>"} ได้ด้วย
  • ถอด env SGI_STA_COMPENSATE_DATA_NAME และ SGI_STA_COMPENSATE_MAX_ITEMS แล้ว

แทน web service /fgiService/updateCompensateFromFS ของระบบเดิม (ManageCompensateController.manageCompensateFromFs) · ตรรกะการบันทึกไม่เปลี่ยนจากฉบับก่อน

ประวัติ: ฉบับ 2026-10-14 ให้ STA เรียกตรงด้วยซองข้อความ → 2026-10-16 เปลี่ยนเป็น STA ส่ง RabbitMQ แล้ว EAI consumer ส่งซองทั้งก้อนมาที่ API → 2026-10-27 กลับมาให้ STA เรียกตรง ด้วยรูปรายการเดียวแบบระบบเดิม (config sta_cal_sgi ของ EAI consumer เลิกใช้)

HTTPเมื่อไรรูปคำตอบ
400body เป็น JSON ที่อ่านไม่ได้ (เช่นวงเล็บไม่ครบ) — ถูกปฏิเสธก่อนถึงตัวประมวลผลรูป error ของ store-backend { "success": false, "data": null, "error": { "code": "BAD_REQUEST", "message": "Unexpected end of JSON input" } } · แก้ JSON แล้วส่งใหม่
401ไม่ส่ง x-api-key หรือค่าไม่ถูกต้องรูป error ของ SGI { "success": false, "data": null, "error": { "code": "UNAUTHORIZED", "message": "…" } }
500body ใหญ่เกินเพดานของ store-backend (100 MB)รูป error ของ store-backend — คำขอปกติเล็กกว่านี้มาก
5xx · timeoutระบบขัดข้องก่อนถึงตัวประมวลผล— ส่งซ้ำได้

คำขอที่ถูกปฏิเสธก่อนถึงตัวประมวลผล (400 · 401 · 500 ของตารางนี้) ไม่มีแถวใน integration_log

ข้อควรรู้

  • ลำดับ: SGI ส่งข้อมูลงวดให้ STA ก่อน (Job 6 · ข้อความ RabbitMQ sgi_impact_store — ขาไป ยังเป็น RabbitMQ เหมือนเดิม) STA คำนวณแล้วเรียก API นี้ส่งยอดกลับ · ส่งยอดของร้านและงวดที่ SGI ยังไม่มีเลย SGI จะสร้างคู่ร้าน (created_by = STA) รอบ และงวดให้แบบระบบเดิม
  • ส่งซ้ำได้: ส่งรายการเดิมซ้ำจะบันทึกทับด้วยค่าเดิม ไม่เกิดข้อมูลซ้ำ จึงลองใหม่ได้เมื่อ timeout · 5xx · IF01004 · IF01004 rollback ทั้งรายการ จึงไม่มีแถวใน sgi_interface_transactions (มีแค่แถวใน integration_log)
  • หนึ่งคำขอ หนึ่ง transaction: ล็อกตาม (ร้าน, งวด) · ล้ม = rollback ทั้งรายการ
  • สถานะงวด: Z ตั้งงวดเป็นยอดศูนย์ · W ตั้งงวดเป็นอยู่ระหว่างชดเชยเฉพาะงวดที่ยังว่างหรือเป็นยอดศูนย์ · งวดที่มีผลอนุมัติแล้ว (อนุมัติ · ไม่ชดเชย · หยุดชดเชย) ไม่เขียนทับ (ตอบ result 1 พร้อม errorMsg บอก)
  • เอกสารที่ออกแล้ว: งวดที่ออกเอกสารแล้วและเอกสารยังไม่จบ SGI รีเฟรชยอดหัวเอกสารและยอดรายร้านเปิดใหม่ให้ในทรานแซกชันเดียวกัน · รอบที่ยอดศูนย์ครบจำนวนงวด ตั้ง/ล้างเดือนสิ้นสุดให้
  • ปี: periodImpact ในคำขอเป็น พ.ศ. · ข้อความใน errorMsg อ้างงวดเป็น ค.ศ. YYYY-MM
  • บันทึก: สองที่
    • integration_log ของระบบ SBP (แทน FGI_WS_LOG ของระบบเดิม) — 1 แถวต่อคำขอทุกผล (สำเร็จ · IF01001 · IF01003 · IF01004) · module = sgi · service = /sgi/interface/sta-update-compensate · payload เป็น JSON: wsName (UPDATE_STORE_COMPENSATE) · requestId · เวลาเริ่ม/จบ · result errorCode errorMsg · outcome · เหตุภายใน · body ที่รับ (dataInput ตัดที่ 20,000 ตัวอักษร · ค่าของคีย์ลับไม่ถูกเก็บ) · คำตอบที่ส่ง (dataOutput) · เขียนนอกทรานแซกชันหลักหลังได้ผล — IF01004 ก็มีแถว · เขียน log ล้มไม่ทำให้คำตอบเปลี่ยน · dryRun ไม่บันทึก
    • sgi_interface_transactions (direction = IN · data_name = STA_UPDATE_COMPENSATE) — ผลละเอียดของรายการที่ผ่านรูปแบบแล้วและถึงขั้นบันทึก (outcome · ร้านที่หาไม่เจอ · เอกสารที่รีเฟรช) · 1 แถวต่อร้าน+งวด (ส่งซ้ำทับแถวเดิม) · status = COMPLETED เมื่อตอบ STA result 1 รวมกรณีหาคู่ร้านเปิดใหม่บางร้านไม่เจอ
  • ทดสอบ: ใส่ ?dryRun=true เพื่อตรวจรูปแบบและดูผลโดยไม่บันทึก

เรื่องที่ขอให้ทีม STA ยืนยัน

  • รูปแบบ periodImpact ที่ส่งจริงเป็น yyMM พ.ศ. ใช่หรือไม่
  • ฝั่ง STA จะส่ง JSON รายการตรง ๆ หรือส่งรูปเดิม {"input":"<base64>"}
  • IP หรือเครือข่ายต้นทางที่จะเรียก API — เพื่อเปิดทางเข้า store-backend
  • ผู้รับ x-api-key และช่องทางรับ key
  • ฝั่งที่อ่านคำตอบรับ Content-Type: application/json ได้ (ระบบเดิมตอบ text/html · เนื้อหาเป็น JSON รูปเดียวกัน)
