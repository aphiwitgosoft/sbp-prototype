SGI รับยอดเงินชดเชยประกันรายได้จาก STA

สัญญา API สำหรับทีม STA — ใช้แทนการส่งข้อความ sta_update_compensate เข้า RabbitMQ เดิม เนื้อข้อความ (ซอง + รายการ) เหมือนเดิมทุกฟิลด์ ต่างกันแค่ช่องทางเปลี่ยนเป็น HTTP

ฉบับ 2026-10-14 · ผู้ให้บริการ: ระบบประกันรายได้ (SGI) บนพอร์ทัล SBPM

Endpoint

POST{BFF base URL}/sgi/workflow/sta-update-compensate

{BFF base URL} ของแต่ละสภาพแวดล้อม (UAT · Production) ทีม SGI จะส่งให้แยก

Headerค่า
AuthorizationบังคับBearer <token> — token ที่ทีม SGI ส่งให้ทางช่องทางปลอดภัย
Content-Typeบังคับapplication/json (UTF-8)
X-Request-Idไม่บังคับรหัสอ้างอิงคำขอของฝั่ง STA — SGI เก็บไว้ในบันทึก interface ใช้ไล่ปัญหาร่วมกัน

เนื้อคำขอ (ซองข้อความ)

ฟิลด์ความหมาย
dataNameบังคับต้องเป็น sta_update_compensate
dataMessageบังคับarray ของรายการยอดชดเชย อย่างน้อย 1 รายการ ไม่เกิน 500 รายการต่อคำขอ
dataTypeไม่บังคับเช่น message
senderไม่บังคับเช่น STA
sentAtไม่บังคับเวลาที่ส่ง (ISO 8601)
dryRunไม่บังคับtrue = ตรวจข้อมูลและตอบผลอย่างเดียว ไม่บันทึก (ใช้ทดสอบ)

ห้ามส่งฟิลด์อื่นนอกจากที่ระบุ ทั้งระดับซองและระดับรายการ ฟิลด์ที่ไม่รู้จักระดับซอง = ปฏิเสธทั้งคำขอ (400) · ระดับรายการ = รายการนั้นเป็น INVALID

รายการใน dataMessage — 1 รายการ = ร้านถูกกระทบ 1 ร้าน × 1 งวด

ฟิลด์รูปแบบ / ความหมาย
storeCodeIบังคับรหัสร้านถูกกระทบ ตัวเลขไม่เกิน 5 หลัก (เช่น 10221 หรือ 221 — SGI เติมศูนย์หน้าให้)
periodImpactบังคับงวด พ.ศ. รูป yyMM เช่น 6906 = มิ.ย. 2569 · รับ yyyyMM พ.ศ. (256906) ได้ด้วย
impactStatusบังคับW = ยอดชดเชยไม่เป็นศูนย์ · Z = ยอดชดเชยเป็นศูนย์
forecastไม่บังคับยอดชดเชยที่ STA คำนวณ (บาท)
adjustไม่บังคับยอดชดเชยหลังปรับ (บาท)
totalStoreCodeNไม่บังคับจำนวนร้านเปิดใหม่ในงวดนี้
compensateไม่บังคับarray ยอดแยกรายร้านเปิดใหม่ (ตารางถัดไป) · ห้ามมีร้านซ้ำในรายการเดียวกัน

รายการใน compensate — ร้านเปิดใหม่ 1 ร้าน

ฟิลด์รูปแบบ / ความหมาย
storeCodeNบังคับรหัสร้านเปิดใหม่ ตัวเลขไม่เกิน 5 หลัก
forecastNไม่บังคับยอดที่ร้านเปิดใหม่ต้องรับผิดชอบ ตามที่คำนวณ (บาท)
forecastPercentNไม่บังคับสัดส่วน % ตามที่คำนวณ
adjustNไม่บังคับยอดหลังปรับ (บาท)
adjustPercentNไม่บังคับสัดส่วน % หลังปรับ
updateBy · createByไม่บังคับผู้บันทึกฝั่ง STA — SGI เก็บ updateBy (ไม่มีจึงใช้ createBy)
openDateN · createDate · updateDateไม่บังคับรับได้ แต่ SGI ไม่ได้ใช้

ตัวเลขส่งเป็น number หรือข้อความตัวเลขก็ได้ (คั่นหลักพันด้วย , ได้) · ค่าว่างหรือ null = ไม่มีค่า

คำตอบ

HTTP 200 เมื่อรับคำขอได้ — แม้บางรายการบันทึกไม่ได้ ให้ดูผลที่ data.status และ data.results ทุกครั้ง

{
  "success": true,
  "data": {
    "status": "PARTIAL_FAILED",
    "dryRun": false,
    "total": 2,
    "updatedCount": 1,
    "newStoreNotFoundCount": 0,
    "notFoundCount": 1,
    "invalidCount": 0,
    "results": [
      { "index": 1, "storeCodeI": "10221", "period": "2026-09", "outcome": "UPDATED",
        "compensationRows": 1, "newStoreUpdated": 1, "newStoreInserted": 0, "newStoreNotFound": [] },
      { "index": 2, "storeCodeI": "00512", "period": "2026-09", "outcome": "NOT_FOUND",
        "compensationRows": 0, "newStoreUpdated": 0, "newStoreInserted": 0, "newStoreNotFound": [],
        "reason": "ไม่พบงวดค่าชดเชยของร้านและงวดนี้" }
    ]
  }
}

period ในคำตอบเป็น ค.ศ. รูป YYYY-MM · index คือลำดับรายการในคำขอ เริ่มที่ 1 · ข้อความใน reason เป็นตัวอย่าง

data.status

ค่าความหมาย
SUCCESSทุกรายการบันทึกสำเร็จ
PARTIAL_FAILEDบางรายการบันทึกไม่ได้
FAILEDไม่มีรายการไหนบันทึกสำเร็จ

results[].outcome

ค่าความหมายต้องทำอะไร
UPDATEDบันทึกยอดของรายการนี้แล้ว—
NEW_STORE_NOT_FOUNDบันทึกยอดร้านถูกกระทบแล้ว แต่ร้านเปิดใหม่บางร้านไม่ได้จับคู่กับร้านนี้ในระบบ SGI (รายชื่ออยู่ใน newStoreNotFound)ตรวจรหัสร้านเปิดใหม่ แล้วส่งรายการนั้นซ้ำ
NOT_FOUNDSGI ยังไม่มีงวดค่าชดเชยของร้านและงวดนี้ (หรือรอบชดเชยปิดไปแล้ว)ตรวจว่าเคยได้รับข้อความงวดนี้จาก SGI แล้วหรือยัง
INVALIDข้อมูลของรายการนี้ผิดรูปแบบ (เหตุอยู่ใน reason)แก้ข้อมูลแล้วส่งรายการนั้นซ้ำ

เมื่อปฏิเสธทั้งคำขอ

{ "success": false, "data": null, "error": { "code": "VALIDATION", "message": "…" } }
HTTPเมื่อไร
401ไม่มี Authorization: Bearer หรือ token ไม่ถูกต้อง
400ซองผิดรูปแบบ · dataName ไม่ใช่ sta_update_compensate · dataMessage ว่าง · เกิน 500 รายการ · มีฟิลด์ระดับซองที่ไม่รู้จัก
5xx · timeoutระบบขัดข้องชั่วคราว — ส่งซ้ำทั้งคำขอได้

ข้อควรรู้

  • ลำดับ: SGI ส่งข้อมูลงวดให้ STA ก่อน (ข้อความ sta_compensate_status ทาง RabbitMQ) STA จึงคำนวณและส่งยอดกลับด้วย API นี้ · ส่งยอดของงวดที่ SGI ยังไม่ได้ส่งมา จะได้ NOT_FOUND
  • ส่งซ้ำได้: ส่งรายการเดิมซ้ำจะบันทึกทับด้วยค่าเดิม ไม่เกิดข้อมูลซ้ำ จึงลองใหม่ได้เมื่อ timeout หรือได้ 5xx
  • รายการแยกกัน: แต่ละรายการบันทึกแยกกัน รายการที่ผิดไม่ทำให้รายการอื่นไม่ถูกบันทึก
  • สถานะงวด: เหมือนระบบเดิม — Z ตั้งงวดเป็นยอดศูนย์เสมอ · W ตั้งงวดเป็นอยู่ระหว่างชดเชยเฉพาะงวดที่ยังว่างหรือเป็นยอดศูนย์ งวดที่มีผลอนุมัติแล้วคงเดิม
  • ปี: periodImpact ในคำขอเป็น พ.ศ. ส่วน period ในคำตอบเป็น ค.ศ.
  • ทดสอบ: ส่ง "dryRun": true เพื่อตรวจรูปแบบและดูผลรายรายการโดยไม่บันทึก
  • ช่องทางเดิม: หลังเปลี่ยนมาใช้ API นี้ ไม่ต้องส่ง sta_update_compensate เข้า RabbitMQ อีก
